**Goal:** 冻结第二平台真实 PoC 的执行目标、前置条件、代码锚点、验证范围与验收骨架，确保后续真实平台 bring-up 是在验证当前 Host 通用框架的充分性，而不是用 PoC 过程去临时掩盖 15 / 17 / 18 / 19 号文档尚未收口的问题。

**Architecture:** 本文件把第二平台真实 PoC 拆成 4 个必须分别回答的问题面：

1. 平台与 transport 选择规则
2. port scaffold 与构建分发闭环
3. 真实板上的最小控制面 / 数据面验证闭环
4. port contract 充分性结论与回流规则

这 4 个面共同决定第二平台 PoC 是“验证通用框架”的动作，还是“在真实板上继续补框架”的动作。20 号文档的价值就在于把两者区分清楚。

**Tech Stack:** 当前以现有 Host core / port / shared RPC glue / common protobuf-c / docs / zephyr 占位目录为现实基线；当前版本已纳入第一轮代码核查、step 级工作包与验证动作。默认候选方向仍为 Zephyr + nRF52 级真实 Host 板 + SPI Full-Duplex + ESP32-C6，但尚未把它写死成已启动执行状态。

**T-shirt size:** M-L（净工程量预计 6.5–13.5 天；若板卡、连线、电平与双串口日志路径未就绪，则 WP 4-5 需明显上调）

## 1. 当前仓库基线与执行问题边界

### 1.1 为什么 20 号文档必须在 18 / 19 之后再写

17 号文档已经明确：20 号文档的验证范围必须引用 17 + 18 + 19 已经固定下来的完成口径，而不能自己改写“什么叫完成”。

原因很直接：

1. 如果 18 号文档尚未定义共性 transport 基线，20 号文档就无法判断第二平台 bring-up 证明了什么。
2. 如果 19 号文档尚未定义 SPI-HD 专题边界，20 号文档一旦选到 SPI-HD，就会把 transport 共性问题和专题问题混在一起。
3. 如果 17 号文档的统一口径不先冻结，第二平台 PoC 很容易被误写成“已经证明框架完整”的证据。

因此，20 号文档不是新的设计起点，而是已有边界稳定后的执行承接文档。

### 1.2 当前仓库现实的最小锚点

本文件后续所有判断，都以以下文件作为最小现实锚点：

### 1.3 当前执行层面的现实阻塞

根据 [9.Host通用化实施总路线图.md](./9.Host通用化实施总路线图.md) 与当前仓库结构，20 号文档必须正视以下事实：

1. 当前第二平台真实硬件执行条件尚未具备，主机板、板级连线、双串口日志与真实 bring-up 条件仍是阻塞项。
2. 当前 `host/port/` 下尚无第二平台目录；从仓库实际看，尚不存在 `host/port/zephyr/` 这类正式 port。
3. 当前 `zephyr/host_poc/` 下只剩空的 `boards/` 目录，`CMakeLists.txt`、`prj.conf`、`src/main.c` 等 PoC 工程最小闭包均不存在。
4. 当前 `h_port_config.h` 仍不能把构建正式分发到第二平台 port，这意味着“真实 PoC 已可执行”在代码现实上并不成立。
5. [14.门槛5-第二平台PoC-实施计划.md](./14.门槛5-第二平台PoC-实施计划.md) 曾引用的 `zephyr/HARDWARE.md` 在当前仓库中已不存在，旧预案中的硬件落点需要在 20 号文档或未来 `zephyr/host_poc` README 中重建，而不能继续假定已有配套说明。

因此，20 号文档当前应被定义为“执行骨架 + 阻塞条件冻结”，而不是“可直接照单上板的详细 bring-up 手册”。

### 1.4 当前还不能假设的事情

当前版本的 20 号文档，不能先验地假设以下事情已经成立：

1. 只要第二平台实现 port contract，真实 PoC 就一定成功
2. 18 号文档定义的共性基线已经全部在代码中收口
3. 14 号文档中的候选平台、硬件方案与工作顺序在今天仍可直接执行
4. 第二平台首发 transport 已经确定必须是 SPI-HD 或 SDIO
5. 第二平台 PoC 一定要以完整功能面为目标，而不是先完成最小控制面 / 数据面闭环

这些都必须等待硬件条件、执行范围和 18 / 19 号文档边界进一步稳定后，才能写成执行既定事实。

## 3. 设计决策记录

### 决策 1：20 号文档显式继承 15 号方法，而不是复制 15 号结构

15 号文档已经解决“新平台一般怎么移植”的问题。

因此，20 号文档当前需要做的不是再写一遍：

1. 应创建哪些 port 文件
2. 平台 app scaffold 如何组织
3. 通用物理 bring-up 条件有哪些

20 号文档应做的是：

1. 选择一个真实第二平台执行这些方法
2. 明确当前仓库现实是否具备执行条件
3. 定义 PoC 完成后要把什么结论回流给 15 / 17 / 18 / 19

### 决策 2：20 号文档只验证统一口径，不改写统一口径

17 号文档已经固定 transport 快速查阅表和对外表述边界。

因此，20 号文档：

1. 只能基于 17 号文档定义的 transport 状态选择验证范围
2. 不能自行把某个 transport 写成“已完成”
3. 不能把 PoC 成功直接外推成“Host 通用框架已完成”

### 决策 3：第二平台首发验证范围默认优先选择较低板级风险的共性 transport

结合 [9.Host通用化实施总路线图.md](./9.Host通用化实施总路线图.md) 的门槛 5 建议和 [17.完成度口径、验证体系与兼容层退场-实施计划.md](./17.完成度口径、验证体系与兼容层退场-实施计划.md) 的 transport 快速查阅表，20 号文档当前默认采用以下选择原则：

1. 首发 PoC 应优先选择能验证真实总线 / IRQ / 数据面、且板级门槛较低的共性 transport
2. 若只做最小控制面探测，UART 可作为低门槛探针，但不能替代门槛 5 的真实数据面证据
3. SDIO 和 SPI-HD 不应作为默认首发路径，除非硬件条件与专题边界已经明显更成熟

这意味着：当前版本可以把“Zephyr + 真实 Host 板 + SPI Full-Duplex”视为默认候选方向，但不能把它写成已经锁定并可立即执行的方案。

### 决策 4：PoC 暴露 contract 不足属于正产出，不属于负结论

9 号文档已经明确：门槛 5 的价值之一，就是让第二平台真实执行去暴露 contract 不充分之处。

因此，20 号文档不应把以下情况定义成单纯失败：

1. `h_transport_contract_t` 在真实平台上暴露 bus / IRQ / DMA 语义不足
2. `h_event_contract_t` 在第二平台线程模型上暴露边界不清
3. `h_osal_contract_t` 的内存、线程、同步假设在真实平台上需要补充限制条件

这些都应该作为 PoC 的核心输出之一，被记录进“port contract 充分性结论”。

## 4. 第二平台真实 PoC 的目标定义

### 4.1 本文所说的“第二平台真实 PoC”是什么

在 20 号文档语境下，“第二平台真实 PoC”至少包括以下 4 个方面：

1. 非 ESP-IDF / 非 Linux mock 的真实平台构建与运行路径
2. 最小控制面闭环在真实板上的成立证据
3. 最小数据面验证在真实板上的成立证据
4. 对 port contract 充分性的显式结论输出

### 4.2 本文所说的“执行条件具备”是什么

在 20 号文档语境下，执行条件具备不等于“仓库里有个目录占位”，而是指：

1. 第二平台硬件、连线、日志通路已明确
2. 选定平台的 port scaffold 已经存在
3. 构建系统能够真正落到第二平台 port，而不是继续使用 Linux fallback
4. 选定 transport 的验证范围与 17 / 18 / 19 号文档边界不冲突

### 4.3 20 号文档最终要证明什么

20 号文档最终需要证明的，不是“所有平台都已被证明可移植”，而是：

1. 至少一个真实第二平台已经完成最小控制面闭环
2. 至少一个真实第二平台已经完成最小数据面验证
3. 团队能够基于真实运行结果判断 contract 是否够用、边界是否合理、哪些问题应回流到框架设计层

## 5. 与 15 / 17 / 18 / 19 号文档的边界

### 5.1 20 号文档如何继承 15 号文档

20 号文档必须显式继承 15 号文档中以下内容，而不是自建一套新规则：

1. 新平台最小 port 文件集合
2. 平台 app / build scaffold 的职责边界
3. 物理 bring-up 条件与平台验证思路
4. 新平台完成接入后应交付的文档集合

20 号文档只负责回答：在当前仓库和当前硬件条件下，哪一条真实平台路径值得先执行、当前卡在哪里、如何形成真实 PoC 证据。

### 5.2 20 号文档如何继承 17 号文档

20 号文档必须服从以下约束：

1. 只能引用 17 号文档已经冻结的 transport 状态定义
2. 只能在 17 号文档允许的对外表述边界内解释 PoC 结果
3. 第二平台 PoC 前后的口径变化，必须回落到 17 号文档的表述矩阵里，而不是在 20 号文档另写一套

### 5.3 20 号文档与 18 号文档的边界

20 号文档不负责：

1. 定义通用 transport 基线最小能力集合
2. 定义 transport 生命周期与协商的共性主链路
3. 定义控制面最小独立生命线的完成标准

20 号文档只验证：这些定义在第二平台上是否形成了真实成立证据。

### 5.4 20 号文档与 19 号文档的边界

只有当第二平台真实 PoC 真的选择 SPI-HD 作为验证 transport 时，20 号文档才需要额外继承 19 号文档的专题边界。

在当前骨架阶段，20 号文档不能：

1. 默认第二平台必须验证 SPI-HD
2. 以第二平台 bring-up 为名，重写 SPI-HD 专题协议设计
3. 把 19 号文档的专题验收直接替代第二平台 PoC 的执行验收

## 8. 风险与待决问题

### 风险 1：把 20 号文档写成第二份移植方案

缓解：所有一般性移植方法统一回指 15 号文档，20 号文档只记录真实执行边界、工作包与结果回流。

### 风险 2：在仓库仍无 Zephyr port / app scaffold 时，就把 PoC 当作“待上板执行”状态

缓解：把 `host/port/zephyr/` 缺失、`zephyr/host_poc/` 只剩空 `boards/` 目录写成正式阻塞条件；WP 1-2 先解决仓库闭包问题，再进入真实板 bring-up。

### 风险 3：用 PoC 过程临时补框架，导致验证结论失真

缓解：任何为 PoC 临时加入的旁路、兜底或特判，都必须被显式标注为“不构成框架完成证据”。

### 风险 4：沿用旧 Gate 5 预案时忽略了仓库落点已变化

缓解：14 号文档只作为历史预案输入，不作为当前 20 号文档的直接上位规则；其中 `zephyr/HARDWARE.md` 等已失效落点必须迁回 20 号文档或未来 `zephyr/host_poc` README。

### 风险 5：在未锁定最小业务路径前就追求完整 `esp_wifi_*` 兼容面

缓解：首轮 PoC 默认以 portable `h_*` API、最小控制面 RPC、`scan -> connect -> IP / 网络就绪` 主路径为硬范围；完整 facade 只作为后续增量目标，不作为当前前置条件。

### 待决问题

当前版本保留以下待决问题，待评审通过或硬件到位后正式锁定：

1. Host 板最终是固定 `nRF52840 DK`，还是允许同级 nRF52 SPI 板作为等价替代
2. `native_posix` 是否保留为正式中间阶段，还是在 Zephyr scaffold 很薄时直接并入真实板 bring-up
3. 第二平台 `netif` 接入的最小闭环是否必须以 DHCP / 拿 IP 为唯一硬标准，还是允许“对等网络就绪事件”作为阶段性等价证据
4. 若后续因硬件条件改变首发 transport，是否仍保持 SPI Full-Duplex；若切到 SPI-HD，必须先回到 19 号文档重新套用专题边界

## 10. 代码核查结果（扩写新增）

触发条件满足后，对 5 个最小锚点文件与 2 个仓库目录占位完成第一轮核查。结果如下。

### 10.1 `h_port_config.h` 的平台分发仍停留在 ESP-IDF / Linux 二选一

文件：`host/port/include/h_port_config.h`

- 当前逻辑是：`__has_include("sdkconfig.h")` 时走 ESP-IDF，否则直接 `#include "../linux/h_port_config.h"` 并定义 `H_PORT_USING_LINUX_FALLBACK`
- 现状没有 Zephyr 分支，也没有第二平台专属 `H_TRANSPORT_IN_USE` 来源
- 这意味着：第二平台 PoC 如果不先补平台分发入口，就可能出现“构建通过，但实际继续落到 Linux fallback”的假阳性

**关键发现**：WP 2 的第一优先级不是写大量 Zephyr 实现，而是先把 dispatcher 扩成显式三选一：ESP-IDF -> Zephyr -> Linux mock fallback。否则第二平台 PoC 证据链不成立。

### 10.2 `h_validate_contracts()` 进一步证明 SPI Full-Duplex 仍是首发最低风险路径

文件：`host/port/include/h_port_contract.h`、`host/core/src/h_init.c`

- `h_validate_contracts()` 按编译期选中的 transport 做 fail-fast 校验
- 当前 SPI Full-Duplex 只要求 `.init`、`.spi_transfer`、`.gpio_config`、`.gpio_set_intr` 作为最小硬必需入口
- SDIO 与 SPI-HD 对 contract 槽位要求更多；SPI-HD 还额外受 19 号文档专题边界约束

**关键发现**：从当前代码现实看，20 号文档在第 3 节冻结的“默认先做 SPI Full-Duplex”判断仍成立。第二平台首轮 PoC 不应起手把风险抬到 SDIO 或 SPI-HD。

### 10.3 `h_transport_drv.c` 主链路仍带 legacy 编排，20 号 PoC 不能绕开它另建 bring-up 路径

文件：`host/core/src/h_transport_drv.c`

- 当前仍直接调用 `bus_init_internal()`、`ensure_slave_bus_ready()`、`rpc_start()` 等 legacy 编排入口
- SPI-HD 数据线协商仍通过 `h_spi_hd_set_data_lines()` 挂在这条主链路里，说明 transport 生命周期仍集中在此
- 20 号文档如果要验证“真实平台上的通用框架是否够用”，就必须验证这条链在第二平台上的可落地性，而不是绕过它另外写一套 host init 时序

**关键发现**：第二平台第一阶段的“真正成功点”应是 `h_hosted_init()`、私有握手与最小 RPC 跑通，而不是一上来追求完整业务流程或重写 transport lifecycle。

**对 WP 4 的直接影响**：如果 18 号文档在执行过程中继续调整 `bus_init_internal()`、`ensure_slave_bus_ready()`、`rpc_start()` 一类入口的签名、调用时序或收口位置，20 号文档的 WP 4 验证动作必须同步更新并重放；不能沿用旧时序的 bring-up 记录去证明新的主链路已经成立。

### 10.4 `h_serial_if.c` / `h_rpc_core.c` 已集中到 wrapper 主路径，但内部仍桥接 `transport_pserial_*`

文件：`host/core/src/h_serial_if.c`、`host/core/src/h_rpc_core.c`

- `h_serial_if.c` 的 `open/send/read/close` 仍全部桥接到 `transport_pserial_*`
- `h_rpc_core.c` 当前 TX/RX 主路径已改为调用 `h_serial_if_*`
- 因此，控制面已经具备“统一入口”，但还没有达到“完全摆脱 legacy 串口桥”的状态

**关键发现**：第二平台首轮 PoC 应优先走 portable `h_*` API 与最小 RPC 主路径，不应把“完整 `esp_wifi_*` facade 可用”写成当前执行前提；否则 scope 会被控制面兼容层牵着跑偏。

### 10.5 第二平台仓库落点仍是“缺正式工程，不缺方案”

目录：`host/port/`、`zephyr/host_poc/`

- 当前 `host/port/` 只有 `esp/`、`esp-idf/`、`include/`、`linux/`，没有 `zephyr/`
- 当前 `zephyr/host_poc/` 下没有任何工程文件，只剩空的 `boards/` 目录
- 14 号文档建议的 `zephyr/host_poc/CMakeLists.txt`、`prj.conf`、`src/main.c`、`boards/<board>.overlay` 目前均未落地
- 14 号文档提到的 `zephyr/HARDWARE.md` 在当前仓库中不存在

**关键发现**：WP 1-2 必须把“仓库最小闭包”本身写进执行范围。20 号文档当前不能把第二平台状态写成“已具备代码入口，只差上板验证”。

### 10.6 14 号预案中仍可复用的结论

文件：`docs/felix/14.门槛5-第二平台PoC-实施计划.md`

- 默认候选路径仍是 Zephyr + nRF52 级 Host 板 + SPI Full-Duplex + ESP32-C6 + `slave/sdkconfig.ci.spi`
- `native_posix` 仍只适合作为中间集成产物，不构成最终验收证据
- `common/proto/esp_hosted_rpc.pb-c.c/h` 与 `common/protobuf-c/protobuf-c/protobuf-c.c` 仍应保持单一来源，不应在 `zephyr/` 下复制第二份
- `host/drivers/rpc/slaveif/` 仍应默认复用，而不是在第二平台起手就重写 RPC glue

**关键发现**：20 号文档可以吸收 14 号文档的执行经验，但必须把其“已变化的硬件落点”和“仍有效的技术路径”分开处理，不能整体照搬。

### WP 5：真实板硬验收，跑通 `scan -> connect -> IP / 网络就绪` 与最小数据面

目标：把 PoC 从“控制面 hello-world”推进到门槛 5 所需的真实业务闭环。

**文件**：`zephyr/host_poc/src/main.c`、必要时 `host/port/zephyr/h_wifi_type_adapt.*`、`host/port/zephyr/h_event.c`

- [ ] Step 5.1：沿 portable `h_*` API 主路径验证最小业务闭环
	- `h_hosted_init()`
	- `h_wifi_init()`
	- `h_wifi_start()`
	- `scan`
	- `set_config`
	- `connect`

- [ ] Step 5.2：明确“硬验收成功点”
	- 首选标准：连接成功 + DHCP / 拿 IP
	- 若第二平台网络栈接入方式不同，允许阶段性记录“对等网络就绪事件”，但不能把它永久替代最终硬验收
	- **仅当以下条件同时满足时**，“对等网络就绪事件”才可作为阶段性等价证据：
	  1. 第二平台 `netif_create` / DHCP client 尚未完整接入，且缺口已明确归类为 netif 集成问题，而不是 transport / RPC / 控制面失败
	  2. Wi-Fi connected 事件已经真实成立
	  3. 已通过至少一条最小数据面验证（`ping`、UDP 发收或等价回环）证明 RX / TX 路径成立
	  4. 验收记录已显式声明：该阶段结论不替代最终“DHCP / 拿 IP”硬验收
	- **排除条件**：如果问题根因仍可能位于 transport、RPC、控制面或事件桥接，则不得用“对等网络就绪事件”替代 DHCP / 拿 IP 结论
	- **阶段性等价条件**：只有当 `netif_create/destroy` 在第二平台尚未完成到 DHCP client 级闭环、且 Wi-Fi connected 事件已经成立、同时至少一个最小数据面验证（`ping` 静态对端或 UDP echo）成功时，才允许把“对等网络就绪事件”记为阶段性等价证据
	- **排除条件**：如果问题根因仍可能位于 transport、RPC、控制面或事件桥接，则不得用“对等网络就绪事件”替代 DHCP / 拿 IP 结论

- [ ] Step 5.3：补最小数据面验证
	- `ping`
	- 或最小 UDP 发收
	- 目标不是测吞吐，而是证明 netif / RX / TX 路径真实成立

- [ ] Step 5.4：失败要回流成 contract 结论，而不是藏进 PoC 特判
	- 若事件到了、Wi-Fi 连上了、但拿不到 IP，应优先判断 `netif` contract 是否颗粒度不足
