# 嵌入式跨平台设计模式

> **核心问题**：嵌入式跨平台只有一个核心矛盾——片上外设和 OS 原语没有标准，但上层业务逻辑完全一样。C 语言写出的应用不关心下面是 FreeRTOS 还是 Zephyr，是 STM32 的 SPI 还是 ESP32 的 SPI。移植层的全部价值就是**统一上层对下层的调用方式，隔离下层对上层的实现变化**。

---

## 1. 模式一览

| # | 模式 | 一句话 | 代表作 | 适合 |
|:---:|------|--------|--------|------|
| 1 | **vtable 合约** | 把平台差异装进函数指针结构体 | Linux VFS, Zephyr driver API, FreeRTOS portable | MCU BSP / HAL |
| 2 | **条件编译** | `#ifdef STM32` 选代码路径 | Arduino, LVGL lv_drv_conf, 老式 BSP | 2-3 个平台的简单项目 |
| 3 | **代码生成** | devicetree/Kconfig → 编译出适配代码 | Zephyr, Linux DTS | 50+ 平台的 RTOS |
| 4 | **HAL 分层** | 硬件驱动 → HAL API → 中间件 → 应用 | STM32Cube, ESP-IDF | 单厂商多芯片 |
| 5 | **OSAL 适配** | `h_malloc` → `malloc` \| `k_malloc` \| `pvPortMalloc` | lwIP, Mbed TLS | 协议栈跨 RTOS |
| 6 | **Wrapper 二次封装** | 薄封装 API，把平台 API 映射到统一接口 | AWS IoT Device SDK, MicroPython port | 应用 SDK 跨平台 |

真实项目几乎都是这 6 种模式的组合，没有纯用单一种的。

---

## 2. 各模式详解

### 模式 1：vtable 合约

**思想**：定义一个函数指针结构体，不同平台填充不同的函数。上层代码永远通过结构体调用，不与具体平台 API 直接链接。

```c
// 合约定义（平台无关）
struct dma_ops {
    int (*alloc)(int channel);
    int (*start)(int channel, void *src, void *dst, size_t len);
    void (*wait)(int channel);
};

// STM32 实现
const struct dma_ops stm32_dma = {
    .alloc = stm32_dma_alloc_channel,
    .start = stm32_dma_stream_start,
    .wait  = stm32_dma_wait_transfer,
};

// ESP32 实现
const struct dma_ops esp32_dma = {
    .alloc = esp32_gdma_new_channel,
    .start = esp32_gdma_start,
    .wait  = esp32_gdma_wait_done,
};

// 上层调用
g_dma_ops->start(ch, src, dst, len);
```

**广泛应用的实例**：

| 项目 | 结构体名 | 用途 |
|------|---------|------|
| Linux | `struct file_operations` | 所有文件系统、设备驱动统一接口。字符设备、块设备、socket 全部是文件，`open`/`read`/`write`/`ioctl` 四个指针搞定 |
| Linux | `struct i2c_algorithm` | 所有 I2C 控制器驱动——TI/ST/NXP/GPIO bit-bang 都可以填同一张表 |
| Linux | `struct usb_device_driver` | USB 设备驱动热插拔，一个 probe 指针 + 一个 disconnect 指针 |
| Zephyr | `struct device.api` | 所有设备模型——GPIO/I2C/SPI/Sensor/Display 的统一入口 |
| FreeRTOS | `FreeRTOS/Source/portable/[compiler]/[arch]/port.c` | 每个架构填 task 切换、临界区、tick 定时器 |
| lwIP | `struct netif.output` / `netif.linkoutput` | 网卡驱动只需要填"发一个包"——其余 TCP/IP 全部通用 |
| Mbed OS | `SPI::_owner->acquire()` | 驱动通过 vtable 实现多态 |
| ESP-Hosted | `hosted_osi_funcs_t` (现有) / `h_osal_contract_t` (重构后) | 把 malloc/sem/queue/thread 需求从 ESP-IDF 解耦 |

**优点**：编译后零额外开销，只比直接调用多一次指针解引用。替换一个子系统只需换一个 global struct，不碰其他代码。
**缺点**：函数多的时候填表繁琐（40+ 个指针容易漏）。所有实现必须遵守完全相同的签名约定。

### 模式 2：条件编译

**思想**：用预处理器宏 `#ifdef PLATFORM_X` 在不同代码块之间选择。

```c
#ifdef ESP32
    spi_bus_initialize(SPI2_HOST, &buscfg, SPI_DMA_CH_AUTO);
#elif defined(STM32F4)
    HAL_SPI_Init(&hspi1);
#else
    #error "Unsupported platform"
#endif
```

**广泛应用的实例**：

| 项目 | 方式 | 用途 |
|------|------|------|
| Arduino | `#ifdef ARDUINO_AVR_UNO` / `#ifdef ESP32` | 每种板子一个 `#ifdef` 块，选不同的 pinMode/digitalWrite 实现 |
| LVGL | `lv_drv_conf.h` | 显示屏和触摸驱动配置：`#define LV_USE_TFT_ILI9341 1` |
| FreeRTOS | `portmacro.h` typedef `#if portBYTE_ALIGNMENT == 8` | 不同架构选择不同数据类型大小 |
| MicroPython | `mpconfigport.h` | 每个移植有一个 `mpconfigport.h`，`#define` 不同特性开关 |
| Mbed TLS | `mbedtls_config.h` | 功能裁剪——`MBEDTLS_AES_ROM_TABLES` 用 ROM 表还是运行时生成 |
| 早期 ESP-Hosted | `#ifdef CONFIG_ESP_HOSTED_SPI_HOST_INTERFACE` | Kconfig 选择传输模式 |

**优点**：直观易懂，不需要额外抽象层。适合 2-3 个平台的简单项目。
**缺点**：平台数超过 10 后 `#ifdef` 地狱——代码可读性崩溃，新增平台要修改所有分散的 `#ifdef` 块。

---

### 模式 3：代码生成

**思想**：不手写平台适配代码，用 DSL（devicetree/Kconfig）描述硬件，构建工具自动生成对应 C 代码。

```
my_board.dts 描述:
  "我有一颗 STM32F407, SPI1 接了 ILI9341 屏幕, I2C1 接了 BME280 传感器"

→ 构建系统生成:
  autoconf.h (Kconfig → #define)
  devicetree_generated.h (DTS → 宏)
  driver instance 初始化代码
  pinmux 配置代码
```

**广泛应用的实例**：

| 项目 | 工具 | 用途 |
|------|------|------|
| Zephyr | devicetree + Kconfig + CMake | 硬件描述 → 驱动绑定 → 自动选源文件 → 链接。改一行 DTS 就能从 STM32 切到 nRF52 |
| Linux | Device Tree (DTS/DTB) | ARM/嵌入式 Linux 的标准硬件描述方案。内核启动时解析 DTB，自动匹配驱动 probe 函数 |
| ESP-IDF | Kconfig (`sdkconfig`) → `sdkconfig.h` | 用 `idf.py menuconfig` 选 GPIO/SPI 模式/传输类型，生成 `sdkconfig.h` |
| STM32CubeMX | `.ioc` 项目文件 → HAL 初始化代码 | 图形化选芯片配引脚，自动生成 `main.c` 骨架和 `MspInit()` |
| NXP MCUXpresso | Pins/Clocks/Peripherals 工具 | 类似 CubeMX，生成 pin_mux.c / clock_config.c |
| OpenAMP | Kconfig + CMake | 多核通信框架，根据 SoC 选择 mailbox/vring 实现 |

**优点**：平台数 50+ 时唯一可持续的方案。改配置不改代码，硬件描述和生产代码分离。
**缺点**：需要完整的构建工具链支持。小项目不值得引入 devicetree 编译器、Kconfig 解析器。

### 模式 4：HAL 分层

**思想**：把硬件依赖按层次剥离——最底层是寄存器，中间是 HAL 库，上层是业务逻辑。每层提供固定 API，厂商保证同一系列芯片的 API 一致。

```
应用代码 (传感器算法、通信协议)
  ↓ 调用 HAL API
HAL API (HAL_SPI_Transmit, HAL_GPIO_WritePin)  ← 厂商保证稳定
  ↓
寄存器操作 (具体芯片地址/位定义)                  ← 随芯片变化
```

**广泛应用的实例**：

| 项目 | API 风格 | 跨芯片范围 |
|------|---------|----------|
| STM32Cube HAL | `HAL_SPI_Transmit(&hspi1, data, len, timeout)` | STM32F0 → F1 → F4 → G0 → H7 → L4 → U5——同一个 API 覆盖全系列 |
| ESP-IDF | `spi_device_transmit(spi_handle, &trans)` | ESP32 → S2 → S3 → C2 → C3 → C6 → P4——同一个 API |
| nRF5 SDK / nRF Connect SDK | `nrf_drv_spi_transfer(&spi, tx_buf, len, rx_buf, len)` | nRF51 → nRF52 → nRF53 → nRF91 |
| Raspberry Pi Pico SDK | `spi_write_read_blocking(spi, src, dst, len)` | RP2040（单芯片但示例了这种风格） |
| Renesas FSP | `R_SPI_Open(&ctrl, &cfg)` | RA 系列全型号 |

**优点**：单厂商多芯片场景下开发效率最高——换了芯片，API 不变，只需重新配置引脚和时钟。
**缺点**：跨厂商不互通。STM32 的 `HAL_SPI_Transmit` 和 ESP32 的 `spi_device_transmit` 完全不是一回事。不做额外封装无法跨厂商复用。

### 模式 5：OSAL 适配

**思想**：协议栈或中间件用它自己的 `os_*` 封装函数，不直接调用任何 RTOS API。移植时只需要实现一组 `os_mutex_create` / `os_queue_send` 等函数。

```c
// 协议栈代码（平台无关）
os_mutex_t *mutex = os_mutex_create();
os_mutex_lock(mutex);
// ... critical section ...
os_mutex_unlock(mutex);

// 移植到 FreeRTOS
os_mutex_t *os_mutex_create(void) { return xSemaphoreCreateMutex(); }   // ← 一行

// 移植到 Zephyr
os_mutex_t *os_mutex_create(void) { struct k_mutex *m = k_malloc(...); k_mutex_init(m); return m; }
```

**广泛应用的实例**：

| 项目 | OSAL 层名称 | 抽象了哪些 |
|------|-----------|----------|
| lwIP | `sys_arch.c` → `sys_mutex_new/sys_sem_new/sys_mbox_new/sys_thread_new` | 没有自己的 OSAL 头文件，直接要求移植者实现约 10 个函数 |
| Mbed TLS | `threading_alt.h` | `mbedtls_mutex_init` / `mbedtls_mutex_free` / `mbedtls_mutex_lock` / `mbedtls_mutex_unlock`——只抽象了互斥锁 |
| AWS IoT Device SDK | `platform/` → `PLATFORM_MutexCreate` / `PLATFORM_ThreadCreate` / `PLATFORM_Random` | 完整抽象了线程、互斥锁、时钟、随机数、网络 socket |
| Mbed OS | `rtos/` → `ThisThread::sleep_for()` / `Mutex::lock()` | C++ RAII 风格，背后可有 FreeRTOS/ThreadX/bare metal 三种实现 |
| CycloneDDS | `ddsrt/` → `ddsrt_mutex_init` / `ddsrt_thread_create` / `ddsrt_cond` | 完整抽象了线程、条件变量、互斥锁、时间 |
| 华为 LiteOS | `los_*` → FreeRTOS/CMSIS-RTOS wrapper | 统一封装了任务、队列、信号量、定时器 |
| ESP-Hosted | `hosted_osi_funcs_t` (现有) / `h_osal_contract_t` (重构后) | 完整抽象了 ~40 个 OS 原语 + 日志 + GPIO |

**优点**：协议栈/中间件一次开发，全平台运行。每一个新平台移植只需要实现一次 OSAL 函数，代价极低。
**缺点**：OSAL 函数签名必须足够通用，太特定于某个 RTOS 的特性就没办法放进 OSAL。优先级、affinity、内存保护等高级特性通常放弃。

### 模式 6：Wrapper 二次封装

**思想**：不定义新接口，直接包裹现有平台 API，提供一个统一名字。比 HAL 更薄，比 OSAL 更接近原生。

```c
// Thin wrapper
static inline void my_spi_transfer(void *buf, size_t len) {
#ifdef ESP32
    spi_device_transmit(spi_handle, &t);     // ESP-IDF 原生 API
#elif STM32
    HAL_SPI_Transmit(&hspi1, buf, len, 100); // STM32 HAL 原生 API
#endif
}
```

**广泛应用的实例**：

| 项目 | 封装方式 | 用途 |
|------|---------|------|
| MicroPython | `mp_hal_*` 前缀的函数 + 每个移植一个 `mpconfigport.h` | `mp_hal_stdout_tx_str` / `mp_hal_pin_write` / `mp_hal_ticks_ms`——约 30 个函数，每个移植手写实现 |
| TinyUSB | `tusb_hal/` 按厂商目录 + DCD (Device Controller Driver) | `dcd_init` / `dcd_edpt_open` / `dcd_edpt_xfer`——每个 MCU USB 控制器一个 vtable 实现 |
| LVGL | `lv_port_disp.c` / `lv_port_indev.c` | 用户手写 2 个文件填充 lvgl 的 flush/touch 回调，lvgl 不感知硬件 |
| nrfx (Nordic) | 统一的 nrfx HAL 封装 Nordic 全系列寄存器差异 | `nrfx_spim_xfer` 在 nRF52/nRF53/nRF91 上都有，内部处理寄存器差异 |
| ESP-Hosted port | `host/port/esp-idf/h_transport_spi.c` 等 | 把 `spi_device_transmit` 填进 transport vtable，上层只看到 `g_h_transport.spi_transfer` |

**优点**：改动量最小——不改原有 API 签名，只是换个调用入口。适合已有大量平台代码、不想重构的场景。
**缺点**：如果没有 vtable 配合，就会退化成模式 2（条件编译）。

## 3. 模式选择指南

```
你要支持的平台数量：
  2-3 个    → 条件编译 (#ifdef) 就够了，别过度设计
  3-10 个   → vtable 合约 + OSAL 适配（本项目的选择）
  10-50 个  → vtable + 代码生成 (Kconfig + 构建系统选平台目录)
  50+ 个    → devicetree + 代码生成 (Zephyr/Linux 模式)

你的代码类型：
  底层驱动 (SPI/GPIO)   → HAL 分层 + Wrapper 二次封装
  协议栈 (TCP/IP, TLS)  → OSAL 适配
  应用 SDK (AWS IoT)     → vtable 合约 + OSAL 适配
  GUI (LVGL, emWin)     → Wrapper 二次封装

你的团队规模：
  1 人   → 条件编译，越快越好
  3-5 人 → vtable 合约，有清晰边界
  10+ 人 → 代码生成 + CI，防止协作混乱
```

## 4. ESP-Hosted 的模式选择

ESP-Hosted 当前使用的模式组合：

| 模块 | 用的模式 | 为什么 |
|------|---------|--------|
| `hosted_osi_funcs_t` (现有) | vtable 合约 | 把 ~40 个 OS 原语从 ESP-IDF 解耦 |
| `h_osal_contract_t` + `h_transport_contract_t` (重构后) | vtable 合约 + OSAL 适配 | 拆成 3 个独立 vtable，每个可单独替换/测试 |
| `h_wrapper.h` (重构后) | Wrapper 二次封装 | 统一命名空间，核心层代码只看到 `h_malloc`，不感知平台 |
| `sdkconfig.ci.*` / `Kconfig` | 条件编译 + 代码生成 | Kconfig 选传输模式，生成 `sdkconfig.h`，CMakeLists 条件 include 传输源文件 |
| `host/port/` 目录结构 | vtable 合约 + 目录分离 | 每个平台一个目录，编译时选一个，不混入核心层 |

这三层分层的理由：
- **vtable 解决"接口统一"**——上层永远调 `g_h_osal.malloc()`
- **目录分离解决"构建隔离"**——core/ 不依赖任何平台，port/ 每个平台独立编译
- **wrapper 宏解决"命名空间"**——核心代码写 `h_malloc` 而不是 `g_h_osal.malloc`，更短、更易替换

## 5. 推荐阅读

| 资料 | 学到什么 |
|------|---------|
| Linux `include/linux/fs.h` `struct file_operations` | vtable 的教科书级实现——一切皆文件 |
| Linux `Documentation/driver-api/` | 总线驱动模型——`struct i2c_driver` / `struct spi_driver` |
| Zephyr `include/zephyr/device.h` `struct device` | devicetree 自动绑定到 vtable——代码生成 + vtable 组合 |
| FreeRTOS `portable/` 目录 | 最小移植范例——一个定时器、一个栈切换、一个临界区 |
| lwIP `contrib/ports/` | OSAL 移植——sys_arch.c 实现 10 个函数 |
| AWS IoT Device SDK `platform/` | 商业级 OSAL——完整抽象了线程/锁/时钟/网络/随机数 |
| Mbed OS `platform/` → `rtos/` | C++ 风格的 HAL + OSAL 双层抽象 |
| TinyUSB `src/portable/` | USB 协议栈的 vtable 移植——按厂商分目录，干净利落 |
