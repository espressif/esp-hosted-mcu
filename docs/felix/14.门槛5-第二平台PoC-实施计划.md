## 2. 门槛 5 要验证的不是“能编译”，而是“contract 是否够用”

### 2.1 控制性问题

门槛 4 已经证明：

- host/core 可以脱离 ESP-IDF 专属头文件而独立工作
- mock port 足以持续编译并验证全部 13 个主路径文件

但门槛 5 仍需要回答三个门槛 4 无法回答的问题：

1. `h_transport_contract_t` 这一张大表，到了真实 Zephyr 板上，是否还足够表达 bus + GPIO + IRQ + netif 的全部责任？
2. `h_event_contract_t` 在没有 `esp_event` 的系统中，是否仍能承载 Wi-Fi/IP/Hosted 事件的注册、投递和线程语义？
3. `h_osal_contract_t` 中的线程、队列、定时器、ISR-safe semaphore、aligned allocation 等假设，在 Zephyr 上是否与 core 当前用法兼容？

### 2.2 因此门槛 5 的失败不等于失败

如果第二平台 bring-up 暴露出：

- `netif_create/destroy` 粒度不够
- `gpio_set_intr()` 缺少边沿/active-level/线程语义约束
- `malloc_align()` 对 DMA 缓冲区的约束表达不足
- `wifi_post()` 和 `post()` 的事件线程模型不够清晰

这不是“门槛 5 失败”，而是门槛 5 **成功揭示了 contract 不充分**。这也是门槛 5 的主要价值之一。

## 3. 平台决策：默认选 Zephyr + nRF52 + SPI，SDIO 只做备选

### 3.1 推荐主路径

门槛 5 默认按以下组合执行：

- **RTOS**：Zephyr
- **Host 板**：`nRF52840 DK` 或同级别、社区支持成熟的 nRF52 SPI 板
- **Transport**：SPI Full-Duplex
- **Slave 板**：ESP32-C6
- **Slave 固件配置**：`slave/sdkconfig.ci.spi`

### 3.2 为什么 SPI 是主路径，而不是 SDIO

当前仓库现状决定了 SPI 是更低风险的真实板起点：

1. `host/core/src/h_init.c` 对 SPI contract 的必需校验最小，只要求 `.init` 和 `.spi_transfer` 为硬必需入口。
2. 仓库已经有现成 SPI port 对照实现：`host/port/esp-idf/h_transport_spi.c`。
3. slave 侧已经有稳定的 SPI CI 预设：`slave/sdkconfig.ci.spi`。
4. 仓库已有 SPI 传输文档：`docs/spi_full_duplex.md`。
5. Zephyr 在 SPI + GPIO IRQ + devicetree 这一组能力上远比“起手就做 SDIO”更适合作为第一块真实板验证路径。

因此门槛 5 的原则是：

> **先用 SPI 证明 contract 在真实板上可落地，再决定是否需要第二轮 SDIO 专项验证。**

### 3.3 为什么不把 STM32 + SDIO 作为起手方案

STM32 + SDIO 不是被排除，而是被明确降级为 **备选方案**。原因：

- SDIO bring-up 比 SPI 更重，板级、时序、bus reset、block read/write、IRQ 路径都更复杂
- 一旦起手就做 SDIO，失败时很难判断是 contract 不足，还是 SDIO 板级问题本身
- 门槛 5 的第一目标是“证明真实板 port contract 能跑通”，不是“覆盖所有 transport”

只有在以下情况满足时，才应把 STM32 + SDIO 升为主路径：

- 团队已经有现成可用的 STM32 + ESP slave 线缆与开发板
- 已经明确希望把门槛 5 的核心价值放在 SDIO contract 检验，而不是 SPI 起步验证
- 可以接受更高的 bring-up 不确定性和更长的故障定位周期

### 3.4 `native_posix` 的定位

Zephyr `native_posix` 只作为 **WP 5.3 的中间集成产物** 使用，用来提前暴露：

- `h_osal.c` 映射错误
- `h_event.c` 注册 / 反注册 / post 行为问题
- `h_port_config.h` 与 Zephyr 宏选择逻辑问题

它**不计入**门槛 5 验收，因为它无法验证：

- 真正的 SPI 总线时序
- GPIO 中断边沿
- CP reset / handshake 电平语义
- DMA / cache / 对齐缓冲区问题

## 4. 总体策略：四阶段收口，而不是直接上真机硬怼

门槛 5 建议按以下四阶段推进：

1. **阶段 A：锁定平台与 repo 落点**
   - 选板、选 transport、定目录、定配置入口
2. **阶段 B：先完成 Zephyr port scaffold + `native_posix` 子集验证**
   - 提前把非 transport 问题清掉
3. **阶段 C：切到真实 nRF52 SPI 板跑控制面，再跑 STA 全流程**
   - 这是门槛 5 的核心交付
4. **阶段 D：沉淀 port contract 充分性报告与 CI 策略**
   - 把 PoC 结论制度化，形成 v1 对外口径的最后依据

关键原则：

- **不要把门槛 5 变成 Zephyr 全量适配工程。**
- **不要在没有 `native_posix` 子集验证前，直接把所有失败都留给真实板。**
- **不要在第一块真实板上同时追求 SPI、SDIO、BT、OTA、Network Split。**
- **不要把“contract 暴露出不足”当作失败。** 这恰恰是门槛 5 的设计目的。

### 4.1 粗粒度估算（单开发者、板卡与日志通路已齐）

| WP | 粗粒度估算 | 说明 |
|----|------------|------|
| 5.1 | 0.5–1 天 | 锁板卡、引脚、日志、slave 固件配置 |
| 5.2 | 1–2 天 | scaffold、`h_port_config.h` 分流、Zephyr 构建接线、protobuf-c 接入 |
| 5.3 | 1–2 天 | `native_posix` 跑通 OSAL + event 子集 |
| 5.4 | 2–5 天 | 真实板 SPI / GPIO IRQ / handshake / 最小 RPC bring-up |
| 5.5 | 1–3 天 | scan → connect → IP / 网络就绪 + 最小数据面 |
| 5.6 | 0.5–1 天 | 充分性报告整理与定稿 |
| 5.7 | 0.5–1.5 天 | contract 决策收口、CI、README、连线与构建文档 |

按上述前提，门槛 5 的净工程量大致为 **6.5–13.5 天**。如果板卡、线缆、电平、双串口日志路径尚未就绪，`WP 5.4` 与 `WP 5.5` 的耗时可能再翻倍，因此不能把这部分当作“顺手一天收掉”的工作。若 `host/drivers/rpc/slaveif/` 的共享 RPC glue 在 Zephyr 构建中暴露出额外 ESP-IDF 残留依赖，`WP 5.4` 的估算还应继续上调，而不是硬压在原区间内推进。

## 5. WP 5.1 — 锁定第二平台与硬件方案

### 5.1 目标

把“第二平台”从抽象概念收敛成一套明确、单一路径的硬件与软件组合，避免后续执行中不断在 nRF52 / STM32、SPI / SDIO 之间来回切换。

### 5.2 建议锁定结果

建议默认锁定为：

- Host：`nRF52840 DK`
- RTOS：Zephyr
- Transport：SPI Full-Duplex
- Slave：ESP32-C6
- Slave 固件配置：`slave/sdkconfig.ci.spi`

### 5.3 涉及输出物

本 WP 完成时至少要有以下结果：

- 板卡清单（Host / Slave / 调试器 / 串口）
- Host ↔ Slave 引脚映射表
- transport 选型结论（SPI，且显式说明不走 SDIO 起手）
- slave 侧构建与刷写方案
- 真实日志通路（Host 串口、Slave 串口、必要时逻辑分析仪）

### 5.4 建议记录模板

建议在本阶段直接把以下信息补到 PoC README 或阶段性 note 中：

- Host 板型号 / SoC
- Zephyr board 名称
- Slave 板型号 / SoC
- SPI 引脚：MOSI / MISO / SCLK / CS
- Handshake / DataReady / Reset GPIO
- Host 串口日志口
- Slave 串口日志口
- 电源供给方式

### 5.5 验证

```bash
cd slave
idf.py -DSDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.ci.spi" set-target esp32c6
idf.py build
```

验收标准不是“已经连起来”，而是：

- 平台组合已经锁定
- 不再保留并行主路径
- 后续所有 WP 都围绕这套组合展开

### 5.6 已知陷阱

1. 起手保留“nRF52 SPI / STM32 SDIO 两条都推进”会直接拉爆带宽。
2. 若 slave 侧板卡、线缆、电平方案尚未确认，就不应进入代码实现阶段。
3. 此阶段如果不明确日志通路，后面真实板调试会极度低效。

## 6. WP 5.2 — 建立 Zephyr port scaffold 与文件落点

### 6.1 目标

把第二平台 port 的代码形态固定下来，使它与现有 `esp-idf/`、`linux/` 两个 port 平行，而不是把 Zephyr 适配散落到 core 或其他目录中。

### 6.2 代码落点（建议）

建议新增以下目录与文件：

- `host/port/zephyr/h_port_config.h`
- `host/port/zephyr/h_osal.c`
- `host/port/zephyr/h_event.c`
- `host/port/zephyr/h_transport_spi.c`
- `host/port/zephyr/port_init.c`
- `host/port/zephyr/h_wifi_type_adapt.h`
- `host/port/zephyr/h_wifi_type_adapt.c`

同时新增一个独立的 Zephyr PoC 工程子树，**不要**塞进当前全是 ESP-IDF 工程的 `examples/` 目录。建议：

- `zephyr/host_poc/CMakeLists.txt`
- `zephyr/host_poc/prj.conf`
- `zephyr/host_poc/src/main.c`
- `zephyr/host_poc/boards/<board>.overlay`
- `zephyr/host_poc/Kconfig`（如确有必要）

### 6.2.1 共享层复用边界必须先写死

门槛 5 默认复用以下共享层，不要在 Zephyr 目录再抄一份：

- `host/drivers/rpc/slaveif/` 中的 `rpc_slaveif_*`
- `common/proto/esp_hosted_rpc.pb-c.c/h`
- `host/core/src/h_rpc_req.c` / `h_rpc_rsp.c` / `h_rpc_evt.c` / `h_rpc_core.c` / `h_rpc_wrap.c`

Zephyr 新增职责应集中在：

- `host/port/zephyr/` 内的 OSAL / event / transport / config / port init
- Zephyr PoC app 自身的 board overlay、Kconfig、`west build` 接线
- 必要的 Zephyr 侧 type bridge

对 `rpc_slaveif_*` 必须明确一个原则：

> Gate 5 不以“在 Zephyr 下重写整套 `rpc_slaveif_*`”为目标；默认继续复用共享 RPC glue。只有当真实板证明这层本身仍夹带 ESP-IDF 假设时，才把问题记录进 `WP 5.6 / WP 5.7`，而不是先在计划文档里默认重写。

对 `h_wifi_adapt_*` 则要反过来写清：

- `h_rpc_wrap.c` 当前直接依赖 `h_wifi_type_adapt.h`
- 因此 Gate 5 必须在 `host/port/zephyr/` 提供对应的 `h_wifi_type_adapt.h/.c`，或者提供等价的最小 type bridge
- 第一版只要求覆盖 PoC 主路径实际用到的 `init / scan / connect / country / ap_record / iface-mode-ps-bw` 一组转换，不要求一次性把所有兼容面铺满
- `tests/stubs/rpc_slaveif_stubs.c` 只允许继续用于 mock 链接，不能进入 Zephyr 生产路径

为避免 scope 蔓延，Gate 5 的 Zephyr app 默认优先走 **portable `h_*` API** 主路径；完整的 `esp_wifi_*` 兼容 facade 不作为门槛 5 的先决条件，除非后续明确把“兼容面复刻”也纳入范围。

### 6.2.2 protobuf-c 的 Zephyr 接入策略必须显式化

当前生成代码与 runtime 的关系必须保持单一来源：

- 继续复用 `common/proto/esp_hosted_rpc.pb-c.c/h`
- 继续复用 `common/protobuf-c/protobuf-c/protobuf-c.c` 及其 headers
- 不在 `zephyr/` 目录再复制一份 generated code 或 protobuf-c runtime

Zephyr PoC 工程在 `WP 5.2` 需要显式完成三件事：

1. 把 `common/proto/esp_hosted_rpc.pb-c.c` 编进 Zephyr app 或 library
2. 把 `common/protobuf-c/protobuf-c/protobuf-c.c` 编进 Zephyr app 或 library
3. 在 `prj.conf` 或等效配置里写明该 PoC 所依赖的 libc / heap 约束，不能默认“构建系统会替我兜底”

第一版建议策略：

- 先沿用当前 `rpc__unpack(NULL, ...)` / `rpc__free_unpacked(..., NULL)` 的默认 allocator 路径，把问题缩小到“Zephyr 构建与 bring-up”本身
- 如果真实板上暴露出 heap 可观测性、碎片、最小 libc、或 DMA 缓冲约束问题，再新增显式 `ProtobufCAllocator` 封装，并只改 RPC decode / free 入口，不 fork 生成代码

明确禁止：

- 复用 `tests/stubs/protobuf_c_stubs.c` 进入 Zephyr 生产路径
- 在 `zephyr/host_poc/` 下维护第二份 `esp_hosted_rpc.pb-c.c/h`

### 6.3 为什么不放进 `examples/`

当前 `examples/` 目录默认语义是“ESP-IDF host examples”。如果把 Zephyr app 混进去，会同时造成：

- 构建系统语义混乱
- 文档认知负担上升
- CI 路径过滤复杂化

Zephyr 第二平台 PoC 本质上是 **port-level validation app**，不是当前 ESP-IDF 示例集的一部分。

### 6.4 `h_port_config.h` 必须补的入口

当前 `host/port/include/h_port_config.h` 只支持：

- `sdkconfig.h` 存在时走 ESP-IDF
- 否则 fallback 到 Linux mock

门槛 5 必须把这个逻辑扩展成三选一：

1. ESP-IDF
2. Zephyr
3. Linux mock fallback

建议原则：

- 使用 Zephyr 自身的编译宏进行分流，不要依赖手工 `-D` 魔法值作为长期方案
- 让 `host/core/` 完全不感知 Zephyr 与 ESP-IDF 的差异，所有差异留在 `host/port/` 内部

建议把 dispatcher 形态固定成下面这种顺序，避免后续又回到“靠构建脚本偷偷塞宏”的状态：

```c
#if __has_include("sdkconfig.h")
#include <sdkconfig.h>
#elif defined(__ZEPHYR__) && __has_include(<zephyr/autoconf.h>)
#include <zephyr/autoconf.h>
#include "../zephyr/h_port_config.h"
#else
#include "../linux/h_port_config.h"
#define H_PORT_USING_LINUX_FALLBACK
#endif
```

这里要把三个规则写死：

- 环境判定优先级固定为 **ESP-IDF → Zephyr → Linux mock fallback**
- `host/port/include/h_port_config.h` 只负责做环境选择，不在这里塞 Zephyr 实现代码
- Zephyr 分支中的 `H_TRANSPORT_IN_USE`、`H_PORT_NAME`、`H_PORT_VERSION` 等平台常量全部放到 `host/port/zephyr/h_port_config.h`，不要继续把 ESP-IDF 风格的常量定义留在 dispatcher 里

### 6.5 验证

本 WP 的最小验证是：

- Zephyr port 文件齐备，能被 Zephyr 工程编译系统看到
- `h_port_config.h` 已经能正确落到 Zephyr 分支，而不是继续掉进 Linux fallback
- `common/proto/esp_hosted_rpc.pb-c.c` 与 `common/protobuf-c/protobuf-c/protobuf-c.c` 已被 Zephyr 工程显式接入
- `host/drivers/rpc/slaveif/` 下的共享 RPC glue 已能在 Zephyr 构建中编译通过；如果这里仍有 ESP-IDF 残留依赖，应在 scaffold 阶段提前暴露，而不是拖到 `WP 5.4`

这一阶段的目标仍然不是已经跑板，而是把后续 bring-up 所需的“最小构建闭包”先固定下来。

### 6.6 已知陷阱

1. 不要把 Zephyr 特定 include 混进 `host/core/`。
2. 不要为了图快，在 `host/port/include/` 直接写一堆 `#ifdef __ZEPHYR__` 的实现代码；这里只允许做选择分发。
3. 不要复用 Linux mock 文件名却塞入 Zephyr 逻辑，Zephyr 应有独立 port 目录。

## 7. WP 5.3 — 先用 `native_posix` 跑通 OSAL + event 子集（中间产物，不计验收）

### 7.1 目标

在接触真实板之前，先把 Zephyr port 中最不依赖硬件的部分跑通：

- OSAL contract
- event contract
- `h_port_config.h` 的 Zephyr 选择路径

### 7.2 这一阶段**不做什么**

这一阶段不追求：

- SPI 真实总线收发
- `h_hosted_init()` 全链路成功
- 真正的 CP 握手
- STA 扫描 / 连接

因为 `native_posix` 无法提供真实 transport 语义。

### 7.3 建议实现方式

#### OSAL 映射建议

建议按以下方式把 `h_osal_contract_t` 映射到 Zephyr：

- memory：`k_malloc` / `k_calloc` / `k_free` 或 libc 封装
- thread：`k_thread_create`
- mutex：`k_mutex`
- queue：`k_msgq`
- semaphore：`k_sem`
- timer：`k_timer`
- delay：`k_msleep` / `k_usleep`
- log：Zephyr log subsystem 或薄封装 `printk`

重点不是 API 名称对齐，而是语义对齐：

- 删除线程是否需要 join 语义
- timer callback 所在线程上下文是否与 core 假设兼容
- `sem_give_from_isr()` 是否真的可在 ISR 上下文安全调用

#### Event 实现建议

Zephyr 没有现成的 `esp_event` 等价层。建议不要强行模拟 `esp_event`，而是直接采用与 Linux mock 类似的轻量事件注册表：

- `register_handler` / `unregister_handler`：维护本地 handler list
- `post` / `wifi_post`：通过工作线程或消息队列异步分发

这里有一个关键点：

> 门槛 5 不要求 Zephyr 端复制 ESP-IDF 的事件框架，只要求 portable contract 的行为足够满足 core 当前需要。

### 7.4 这一阶段的验证项

建议至少覆盖：

- `h_validate_contracts()` 通过
- `h_event_register()` / `h_event_post()` / `h_event_unregister()` 正常
- Wi-Fi event 与 Hosted event 分流正常
- `h_thread_create` / `h_queue_*` / `h_timer_*` 基本行为正常

### 7.5 建议验收方式

用 `native_posix` 运行一个最小自测 app 或 Zephyr test binary，验证：

- 初始化不崩溃
- 事件可注册投递
- 队列 / 信号量 / 定时器不会立刻暴露明显语义错位

### 7.6 已知陷阱

1. `native_posix` 成功不代表 transport contract 充分。
2. 如果这一阶段直接追求 `h_hosted_init()` 全链路成功，最后会被 transport stub 误导。
3. Zephyr 的线程 / timer 生命周期语义和 Linux mock 不完全相同，这一阶段就要记录差异。

## 8. WP 5.4 — 在真实板上打通控制面与私有握手

### 8.1 目标

把第二平台从“Zephyr 端已能编译”推进到“真实 SPI 总线、GPIO IRQ、握手、控制面 RPC 都已打通”。

### 8.2 这一步才是真正开始验证 transport contract

真实板 bring-up 至少要覆盖以下路径：

- `g_h_transport.init`
- `g_h_transport.spi_transfer`
- `g_h_transport.gpio_config`
- `g_h_transport.gpio_set_intr`
- `g_h_transport.gpio_read` / `gpio_write`
- `h_port_transport_init()`
- `h_port_rpc_init()`

### 8.3 推荐最小 bring-up 顺序

建议顺序如下：

1. slave 侧刷入 SPI 固件，确认 slave 串口日志正常
2. Host 板 GPIO / SPI devicetree 就绪
3. Host 侧完成 transport init，不要求立刻进 Wi-Fi API
4. 打通 Host ↔ Slave 的私有握手 / init event
5. 跑通 hello-world 级控制面 RPC

建议的第一个“真正有价值”的成功点不是 `scan`，而是：

- `h_hosted_init()` 成功
- 收到 `ESP_HOSTED_EVENT_CP_INIT` 或等价 hosted 事件
- 控制面请求得到响应（如 `h_wifi_init` / `get_mac` / `get_mode` 一类最小 RPC）

### 8.4 推荐日志要求

至少同时保留：

- Host 串口日志
- Slave 串口日志
- 关键 GPIO 状态与 SPI 初始化日志

如果 bring-up 遇到 handshake / IRQ 不稳定，建议再补：

- 逻辑分析仪波形

### 8.5 建议验证命令骨架

Slave 侧：

```bash
cd slave
idf.py -DSDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.ci.spi" set-target esp32c6
idf.py build
```

Host 侧：

```bash
cd zephyr/host_poc
west build -b nrf52840dk_nrf52840 -p always
```

### 8.6 本 WP 验收点

达到以下几点即可视为 WP 5.4 完成：

- Host 侧 transport 初始化成功
- Host 与 slave 完成私有握手
- 至少一个控制面 RPC 成功收到响应
- 相关日志可复现、可归档

### 8.7 已知陷阱

1. 不要把第一次成功点定义得过高，起手就要求 scan/connect 只会拉长定位路径。
2. 如果没有 Host/Slave 双日志，很多 transport 问题根本无法判因。
3. 若 GPIO active-level 或 edge type 未在板级配置里写清，这一步最容易出现“总线有了，事件没进来”。

## 9. WP 5.5 — 在真实板上跑通 STA 全流程（硬验收）

### 9.1 目标

这是门槛 5 的硬验收。不是“控制面 hello-world 成功”，而是：

- scan
- connect
- connected event
- IP 获得或对等网络就绪事件

### 9.2 建议最小业务路径

建议按照以下最小路径执行：

1. `h_hosted_init()`
2. `h_wifi_init()`
3. `h_wifi_start()`
4. `scan`
5. `set_config`
6. `connect`
7. 等待 Wi-Fi connected 事件
8. 等待 IP / DHCP 成功事件

如果第二平台网络栈接入尚不足以完成完整 IP 获取，则至少必须满足：

- Wi-Fi 连接已经真实建立
- 缺口被明确归因为 `netif` contract 或其上层接入问题
- 问题进入 WP 5.6 / WP 5.7 的 contract 报告，而不是被忽略

但按照路线图门槛定义，**最终仍应以“拿到 IP 或对等网络就绪事件”作为硬验收**，不能永久降级成“只连上 AP”。

### 9.3 数据面最小补充验证

建议至少再加一条最小数据面验证：

- `ping`
- 或一组最小 UDP 发收

它不是门槛 5 的主要目标，但它能帮助判断：

- netif 创建是否足够
- RX/TX 数据面是否真实通了
- Wi-Fi event 到 net stack 的桥接是否只停留在日志层

### 9.4 本 WP 验收记录要求

本阶段至少归档以下证据：

- scan 结果日志
- 连接成功日志
- 断开 / 重连日志（至少一次）
- IP / 网络就绪日志
- 最小数据面验证记录

### 9.5 已知陷阱

1. 若事件层能发 Wi-Fi connected，但 netif 没接起来，很容易造成“看似成功，实际没网络”。
2. Zephyr 端网络栈与 ESP-IDF 的 `esp_netif` 完全不同，这里最可能暴露 `netif_create/destroy` 颗粒度不足。
3. 这一步不要追求吞吐；能稳定完成一轮 scan → connect → IP 就够。

## 10. WP 5.6 — 产出 port contract 充分性评估报告

### 10.1 目标

把 PoC 中暴露出的 contract 问题制度化，而不是只留在 commit、聊天记录或串口日志里。

### 10.2 建议新增报告文档

建议在 PoC 完成后新增一份独立报告，例如：

- `docs/felix/15.第二平台PoC-port-contract充分性评估.md`

### 10.3 报告结构建议

建议按 contract 维度逐项评估：

#### A. OSAL contract

- 哪些接口完全够用
- 哪些接口语义能工作，但约束不清晰
- 哪些接口在 Zephyr 上需要补充前置条件或改造

重点关注：

- `thread_delete`
- `timer_start/stop/delete`
- `sem_give_from_isr`
- `malloc_align/free_align`

#### B. Event contract

重点回答：

- 当前 `register/post` 粒度是否足够
- `wifi_post` 是否仍有独立存在价值
- handler 线程上下文是否需要在 contract 中明确

#### C. Transport contract

这是门槛 5 的核心评估项。

重点回答：

- 把 bus、GPIO、IRQ、netif 塞在一张 `h_transport_contract_t` 里是否仍然合理
- 如果存在结构性不足，证据究竟落在 bus、board IRQ / GPIO、还是 netif 哪一块
- 哪些观察应当进入 `WP 5.7`，作为“是否拆分 transport contract”的决策输入
- 当前 `netif_create/destroy` 是否过弱

### 10.4 报告结论必须是明确的

报告结论不能停留在“还行”或“后续再看”，而必须显式给出：

1. **够用，可维持当前 contract 形态**
2. **勉强够用，但必须补语义说明 / 前置条件**
3. **存在结构性不足，必须进入 `WP 5.7` 做 split / no-split 收口决策**

也就是说，`WP 5.6` 负责把证据和评估结论写清；是否真的要拆、拆到哪一层，则放在 `WP 5.7` 收口，而不是让 `WP 5.6` 抢跑做最终结构决策。

### 10.5 已知陷阱

1. 如果不单独写报告，门槛 5 的核心价值会被真实板 bring-up 过程冲掉。
2. 这份报告必须基于真实板观察，而不是基于抽象偏好。
3. 若最终决定“不拆”，也必须明确写出为什么不拆。

## 11. WP 5.7 — 基于 5.6 报告收口 contract 决策、CI、脚本与移植文档

### 11.1 目标

把门槛 5 从一次性 PoC 变成后续团队可重复执行的能力，而不是“只有当前机器、当前开发者才能复现”；同时把 transport contract 是否需要拆分的结论收口成明确决策。

### 11.2 先收口 transport contract 决策

`WP 5.7` 的第一件事不是写 CI，而是消化 `WP 5.6` 报告并给出明确决策。建议只允许以下三种收口结果：

1. 维持单一 `h_transport_contract_t`，仅补语义说明与前置条件
2. 维持 v1 单一 contract，但把 bus / board IRQ / netif 的潜在拆分列为后续强跟踪项
3. 判定当前 contract 已不够，进入后续 split 设计

这里必须明确两点：

- 决策依据只能来自 `WP 5.6` 的真实板证据，而不是抽象偏好
- 不能把“先这样吧，后面再看”留在门槛 5 作为最终结论

### 11.3 CI 策略建议

建议分三层：

#### 基线层：现有 ESP-IDF 回归（不放宽）

Gate 5 虽然引入 Zephyr，但它改动的很多路径仍然是共享路径。因此凡是触及以下目录：

- `host/core/`
- `host/port/include/`
- `host/drivers/rpc/`
- `common/proto/`
- `common/transport/`

就必须继续保留现有 ESP-IDF 基线回归，而不能被“Zephyr 能编了”替代。至少要保持：

- 现有 ESP-IDF host 集成路径可构建
- `slave/sdkconfig.ci.spi` 路径可构建
- `scripts/hw_smoke_test.sh` 在阶段收口时至少跑一次

这一层不一定要成为每个 PR 的强制在线 job，但**不能**从 Gate 5 中消失。

#### 第一层：编译型 CI（必跑）

每次 PR / push 至少跑：

- Zephyr `native_posix` 编译
- Zephyr 目标板编译（如 `nrf52840dk_nrf52840`）

这一层作用是：

- 防止 Zephyr port 再次编译失效
- 防止 `host/core/` 或 `h_port_config.h` 的改动把第二平台构建打断

#### 第二层：真实板 smoke（手动或定时）

真实板 smoke 不应塞进每个 PR 的强制门禁。建议：

- 手动触发
- 或定时任务
- 或 release 前跑

这样可以降低 CI flake 对日常开发的干扰。

### 11.4 文档收口建议

门槛 5 完成后，至少补以下文档：

- Zephyr port README
- 第二平台硬件连线说明
- 第二平台构建 / 刷写 / 日志采集步骤
- Zephyr app 调用面说明（默认 portable `h_*` API，还是额外复刻兼容 facade）
- `h_wifi_type_adapt` 的落点与覆盖范围说明
- protobuf-c 的构建 / allocator 策略说明
- port contract 充分性评估报告

### 11.5 本 WP 验收点

- transport contract 的 split / no-split 决策已归档
- 现有 ESP-IDF 回归约束未被门槛 5 放松
- 编译型 CI 可持续运行
- 真实板 smoke 有明确入口
- 第二平台移植路径对团队其他人可复现

### 11.6 已知陷阱

1. 不要把真实板 job 作为每个 PR 的强制门禁。
2. 不要只留下口头说明，板级连线与构建命令必须文档化。
3. 不要把门槛 5 的结论埋在 README 里而没有独立评估报告。
4. 不要把 Zephyr 编译 CI 加上了，就默认现有 ESP-IDF 生产路径自然安全。

## 14. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| SPI 板级连线 / IRQ 电平问题 | bring-up 长时间无响应 | 在 WP 5.1 就锁定日志通路与引脚表，必要时加逻辑分析仪 |
| Zephyr 事件模型与当前 contract 语义不完全匹配 | 控制面看似通，事件行为不稳定 | WP 5.3 先在 `native_posix` 验证事件层 |
| `netif_create/destroy` 对 Zephyr 不够用 | scan/connect 成功但拿不到 IP | 在 WP 5.6 把它作为 contract 评估重点，而不是临时 patch 掉 |
| 起手就走 SDIO | bring-up 周期显著拉长，难定位 | 默认 SPI 首发，SDIO 只做后续专项路径 |
| scope 蔓延到 BT/OTA/power save | PoC 无限扩张 | 明确门槛 5 只验证最小 Wi-Fi 主路径 |
| 真实板 smoke 直接塞进每个 PR | CI 噪声与 flake 增大 | 采用“ESP-IDF 基线回归 + Zephyr 编译必跑 + 真机手动/定时”的三层 CI |
| Gate 5 修改共享路径导致现有 ESP-IDF 生产路径回归 | Zephyr 看似成功，但主线退化 | 在 `WP 5.7` 保留现有 ESP-IDF baseline regression，不被 Zephyr CI 替代 |

## 15. 门槛 5 完成后的状态定义

门槛 5 完成时，才允许对外使用如下口径：

> Host 通用框架已完成跨平台移植友好型收口；新增平台只需实现 port contract 即可，核心层不再需要平台专属改动。

这里的关键不是 Zephyr 代码本身存在，而是以下三件事同时成立：

1. 第二平台真实硬件跑通了最小 Wi-Fi 主路径。
2. port contract 充分性已经被真实板验证，而不是仅由 mock 推断。
3. 仓库已经留下可复现的 port scaffold、构建路径、日志路径和结论报告。

在这之前，Host 通用框架仍然只能被描述为：

> `host/core/` 已完成 portable / testable / 已验证生产路径闭环，但仍需第二平台真实硬件验证，才能最终确认 port contract 充分性。
