# 门槛 5 — 第二平台 PoC（实施计划 · 轻量骨架版）

> **本文档性质声明**
>
> 这是一个**轻量骨架版**实施计划：仅给出目标、范围、依赖、入口/出口条件、已知风险与待扩写说明。
>
> **不**包含 step 级命令、文件替换块、TDD 步骤等可执行细节。
>
> 真正的 step 级实施计划将在**门槛 4（13 号文档）执行完成后**对本文档进行扩写。
>
> 本文档的权威来源是 `docs/felix/9.Host通用化实施总路线图.md` 中"门槛 5"小节，本文档不复述其论证过程，只承载对该路线图条目的承接。

## 目标

在 ESP-IDF 与 Linux mock 之外，再在一个**真实非 ESP 硬件平台**上完成最小 bring-up，使整个 Host 通用框架在两类异构平台上都可运行、可观测、可演进，从而验证 port contract 的充分性。

Linux mock 已证明"能跑非 ESP 编译"，本门槛证明"能跑非 ESP 真实硬件"，两者**不可互相替代**。

## 范围

### 在范围内（按 9 号路线图 WP 5.1–5.7）

- WP 5.1 — 选定第二平台。**推荐方案**：
  - **方案 A（首选）**：Zephyr + nRF52 + SPI（成熟硬件、Zephyr SPI 子系统稳定、社区参考多）
  - **方案 B**：Zephyr + STM32 + SDIO（覆盖 SDIO 路径，硬件难度更高）
  - **显式排除**：`native_posix` 等 Zephyr 模拟器不计入本门槛验收（与 mock 的覆盖角色重叠）
- WP 5.2 — 在第二平台上提供 OSAL / event / transport 三个 contract 的实现
- WP 5.3 — 把核心层接入选定 transport（SPI 或 SDIO），完成与 ESP slave 的私有 TLV 握手
- WP 5.4 — 跑通最小 Wi-Fi 控制面流程：`init` / `start` / `scan` / `connect` / 断开重连
- WP 5.5 — 跑通最小数据面流程：至少有一个 ICMP 或 UDP 双向通路成功
- WP 5.6 — 在第二平台上跑通 RPC 控制面回归子集
- WP 5.7 — 把第二平台纳入 CI（编译矩阵；真机循环可放定时 / 手动触发）并补齐 README / port 实现文档

### 不在范围内

- 不在第二平台上做完整功能等价验收（Bluetooth、network split、host power save、OTA 等可放后续阶段）
- 不优化第二平台的吞吐 / 延迟 —— 本门槛只判定"通用框架可移植"，不判定"性能可接受"
- 不引入第三个平台
- 本骨架版**不**展开 step 级命令、文件级替换块、TDD 步骤；这些将在扩写阶段补齐

## 依赖

- **强依赖**：门槛 1 / 2 / 3 / 4 全部完成。本门槛是终态验收，缺任意一个都会让"PoC 失败"难以归因
- **建议先行**：在第二平台 bring-up 之前，先在 Linux mock 上跑通门槛 4 的所有 mock 替身路径，作为"虚拟 PoC"先期发现问题
- **不可并行**：本门槛与门槛 1–4 串行；与其他门槛并行执行只会让真实硬件失败时无法判定根因

## 入口条件

- 门槛 1–4 全部完成，且 isolation / mock / 三口径声明已稳定一段时间（建议至少一个 PR 周期）
- 第二平台硬件、调试设施、ESP slave 配套硬件、连线方案已就绪
- 团队已盘点过 OSAL / event / transport contract 当前对 ESP-IDF 行为的假设，明确哪些假设可能在第二平台不成立

## 出口条件 / 验收

参照 9 号路线图门槛 5 的验收口径：

- [ ] 第二平台为 Zephyr + 真实硬件（推荐 nRF52 SPI 或 STM32 SDIO）；`native_posix` 等模拟器不计入
- [ ] 第二平台的 OSAL / event / transport contract 实现存在且可编译通过
- [ ] 第二平台与 ESP slave 完成私有 TLV 握手
- [ ] 第二平台上 `scan` / `connect` / `disconnect` / 断开重连四个控制面动作至少跑通一次
- [ ] 第二平台至少有一组 ICMP 或 UDP 双向通路验证记录
- [ ] 第二平台上 RPC 控制面最小回归通过
- [ ] 第二平台编译纳入 CI；真机测试有可复现脚本与（最少）人工或定时触发记录
- [ ] 第二平台 port 目录有 README / 实现文档，明确移植者可参考的路径

## 已知风险

1. **真实硬件 bring-up 不可压缩**：连线、电源、时钟、SPI/SDIO 时序问题不会在 mock 出现，可能消耗大量时间；估算 1–3 周容易低估
2. **Zephyr 子系统差异**：Zephyr SPI / SDIO 接口与 ESP-IDF 不同，OSAL 假设（如 ISR-safe 队列语义、tickless）需要重新校验
3. **netif / IP stack 接入差异**：Zephyr 用 LwIP 但接入路径与 ESP-IDF 的 `esp_netif` 不同；transport contract 中 netif 责任可能需要在本门槛之后再次拆分（评审已埋下注脚）
4. **CI 真机测试稳定性**：真机抖动会让 CI 噪声增大；需要在引入前明确"哪些 job 必跑 / 哪些可定时跑 / 哪些容忍 flake 重试"
5. **PoC 范围蔓延**：bring-up 一旦顺利容易被加塞 BT、OTA、power save 等需求；需明确本门槛只验证"通用框架可移植"
6. **slave 侧的 ESP-IDF 假设外溢**：本评审整体不覆盖 slave，但第二平台 PoC 可能反推出 slave 端的某些非通用假设；需要把这些发现记录下来给后续 slave 通用化做素材，**不在本门槛内修**
