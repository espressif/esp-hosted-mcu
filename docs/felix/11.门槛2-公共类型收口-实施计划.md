## 目标

把公共头文件中残留的 ESP-IDF 直通类型映射收回到核心层，使 `h_wifi_*` 等公共类型在所有平台上都由核心层独立定义，并通过编译期断言防止与 ESP-IDF 原生类型出现布局 drift。

完成本门槛后，应满足：

- `host/core/include/h_public/h_wifi_types.h` 不再通过 `#ifdef ESP_PLATFORM` 直通包含 `esp_wifi.h`，也不再 `typedef wifi_*_t` 到核心层 alias
- 核心层在所有平台上对外暴露的是同一份 `h_wifi_*_t` 结构体
- ESP-IDF port 层负责在 `h_wifi_*_t` 与原生 `wifi_*_t` 之间做字段级转换
- 关键 `h_wifi_*` 类型存在 `_Static_assert` / `static_assert` / `offsetof` 级别的字段大小、偏移、对齐一致性检查

## 范围

### 在范围内（按 9 号路线图 WP 2.1–2.6）

- WP 2.1 — 列出 `h_wifi_types.h` 中所有目前依赖 `ESP_PLATFORM` 的类型与字段
- WP 2.2 — 在核心层重写这些类型为平台独立定义
- WP 2.3 — 在核心层补齐 `_Static_assert` 等字段布局编译期断言
- WP 2.4 — 在 ESP-IDF port 层实现 native ↔ portable 双向适配函数
- WP 2.5 — 把 RPC / 上层调用路径中"假设核心类型即原生类型"的地方迁移到走 port 层适配
- WP 2.6 — 在 ESP-IDF 与 Linux mock 上同时验证类型边界，补齐 isolation 脚本对 `h_wifi_types.h` 的检查

## 入口条件

- 门槛 1 已完成，或团队已就"什么算 portable"达成口径一致
- 当前 `h_wifi_types.h` 中的 `ESP_PLATFORM` 直通分支已被识别并文档化（即 9 号路线图所列条目仍准确反映主分支状态）
- ESP-IDF port 层目录结构稳定，可承接新增的 native↔portable 适配代码

## 出口条件 / 验收

参照 9 号路线图门槛 2 的验收口径：

- [ ] `h_wifi_types.h` 中不再存在 `#ifdef ESP_PLATFORM` 包含 `esp_wifi.h` 的代码路径
- [ ] `h_wifi_types.h` 中不再存在 `typedef wifi_*_t h_wifi_*_t` 形式的直通别名
- [ ] 关键 `h_wifi_*` 类型存在编译期字段一致性断言，且这些断言在 ESP-IDF 构建中实际生效
- [ ] ESP-IDF port 层提供完整的 `h_wifi_*_t` ↔ `wifi_*_t` 双向转换实现
- [ ] `scripts/check_core_isolation.sh` 移除针对 `h_wifi_types.h` 的临时白名单
- [ ] ESP-IDF 真机或目标 sdkconfig 下 RPC 控制面回归通过
- [ ] Linux mock 在新类型边界下编译通过且既有测试通过

## 已知风险

1. **字段布局 drift**：portable struct 与 ESP-IDF 原生 `wifi_*_t` 长期保持字段一一对应是脆弱的。一旦未来 ESP-IDF 升级改字段，断言会触发编译失败 —— 这是预期行为，但需要明确的 drift 处理流程（升级断言 vs 升级 portable struct）
2. **RPC 路径回归**：现有 RPC wrap 与序列化/反序列化代码可能隐式依赖"核心类型即 ESP 类型"。把这一假设拆掉时，可能在控制面边界出现字段错位
3. **ABI 兼容**：如果有外部代码已经按 ESP `wifi_config_t` 调用核心层 API，类型主权回收会破坏其源码兼容；需要事先盘点对外 API 的实际使用面
4. **断言粒度过细的开发摩擦**：`_Static_assert` 太密会让 ESP-IDF 微小升级频繁触发；需要在"早发现 drift"和"开发摩擦"之间取折中
