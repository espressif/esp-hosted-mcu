**Goal:** 使 `host/core/include/h_public/h_wifi_types.h` 不再通过 `#ifdef ESP_PLATFORM` 直通 typedef 到 ESP-IDF 原生类型;核心层在所有平台上都暴露独立的 `h_wifi_*` 结构体定义;ESP-IDF port 层通过字段级适配函数完成 native ↔ portable 双向转换;`check_core_isolation.sh` 移除对 `h_wifi_types.h` 的临时白名单。

**Tech Stack:** C11(`_Static_assert`)、Bash(`check_core_isolation.sh`)、ESP-IDF 5.4 类型头(参考来源:`examples/host_framework_validation/managed_components/espressif__esp_wifi_remote/idf_v5.4/include/injected/esp_wifi*.h`)。

## 设计决策记录

### 决策 1:承认 portable struct 与 native struct 布局不同,放弃 zero-copy

当前 `h_wifi_types.h` 头部注释声称"Fields mirror ESP-IDF layout for zero-copy mapping"。实际对比 ESP-IDF 5.4 头文件后发现:

- `h_wifi_init_config_t` 的字段顺序、类型(`void*` 错写为指针,实际是 `int`)、缺失字段(`amsdu_tx_enable`、`beacon_max_len` 等)均与 `wifi_init_config_t` 不符
- `h_wifi_config_t` 是 struct(含 `sta`/`ap` 子结构),而 `wifi_config_t` 是 union(含 `ap`/`sta`/`nan`)
- `h_wifi_ap_record_t` 的 `ssid[32]` 比 native `ssid[33]` 少 1 字节;`country` 字段类型不同
- `h_wifi_bandwidth_t` 枚举值(`0`,`1`)与 native(`1`,`2`)不一致

**结论:** 不存在可靠的 zero-copy 路径。所有类型交互必须通过显式字段映射完成。这一事实将写入 `h_wifi_types.h` 头部注释,替换原有误导性声明。

### 决策 2:删除未接入构建的迁移残留文件 `h_rpc_wrap_api.c`

`host/core/src/h_rpc_wrap_api.c` 当前**未被任何 CMakeLists.txt 或构建配置引用**,属于早期迁移尝试的残留文件。它虽然与 `host/api/src/esp_wifi_weak.c` 都提供弱函数,但当前构建图根本不编译它,因此不存在"链接期弱函数冲突"。

删除理由:
1. 它是死代码,清理后减少仓库噪音
2. 其签名混用 `h_err_t` 和 `h_wifi_*` 类型,若未来被误接入构建会造成类型签名歧义
3. 弱函数职责应统一在 `host/api/` 目录下,不应散落在 `host/core/src/`

**注意:** 删除它**不是**解决当前主链路类型失配的关键步骤。真正决定编译是否通过的边界在 `esp_hosted_api.c`/`esp_hosted_api_priv.h` (见决策 4)。

### 决策 3:`_Static_assert` 只做粗粒度检查,不做 offsetof 逐字段断言

由于 portable 与 native struct 字段组织不同,`offsetof(portable.field) == offsetof(native.field)` 的断言不适用。改为:
- `sizeof` 相等或范围检查(发现 drastic size change)
- `_Alignof` 相等检查(发现对齐漂移)
- 对 enum 做值域覆盖检查(如 `H_WIFI_AUTH_MAX == WIFI_AUTH_MAX` 的等价映射验证)

这些断言放在 `h_wifi_type_adapt.c` 中(该文件同时包含 `esp_wifi.h` 和 `h_wifi_types.h`),在 ESP-IDF 构建时生效。

### 决策 4:真实类型转换边界在 `esp_hosted_api.c`/`esp_hosted_api_priv.h`,不在 `esp_wifi_weak.c`

当前架构三层:

1. **Facade 层**: `esp_wifi_weak.c` — 提供 `esp_wifi_*` 弱函数(native 签名),直接转发给 `esp_wifi_remote_*`
2. **Bridge 层**: `esp_hosted_api.c` — 实现 `esp_wifi_remote_*`(native 签名),内部调用 `rpc_wifi_*`(portable 签名)
3. **Core 层**: `h_api.c`/`h_rpc_wrap.c` — 使用 portable 类型

Task 1 删除 ESP_PLATFORM 后,**真正会编译失败的边界是第 2 层**: `esp_hosted_api.c` 以 `wifi_init_config_t*` 调用 `rpc_wifi_init(h_wifi_init_config_t*)`,类型不再兼容。

因此:
- `esp_hosted_api.c` 必须作为**主收口点**,在调用 `rpc_wifi_*` 前把 native 参数转成 portable
- `esp_hosted_api_priv.h` **保持 native 签名不变**,因为 `esp_wifi_weak.c` 包含它并按 native 类型调用;转换发生在 `esp_hosted_api.c` 实现体内部,而非接口声明层面
- `esp_wifi_weak.c` 保持不动,因为它只接触 native 类型,不跨越 portable/native 边界

## Task 6:更新 `esp_hosted_api.c` 作为 native→portable 转换边界

**Files:**
- Modify: `host/api/src/esp_hosted_api.c`

Task 1 删除 ESP_PLATFORM typedef 后,`rpc_wrap.h`(经 Task 4.0 更新)声明的 `rpc_wifi_*` 函数全部使用 `h_wifi_*` portable 类型。但 `esp_hosted_api.c` 实现的 `esp_wifi_remote_*` 函数仍接收 native 类型参数(这是正确的,因为 `esp_wifi_weak.c` 和外部 `esp_wifi_remote` 组件按 native 签名调用它们)。

因此,**`esp_hosted_api.c` 必须成为 native→portable 转换的决策边界**:每个 `esp_wifi_remote_*` 函数在内部调用 `rpc_wifi_*` 之前,把 native 参数转成 portable;对于输出参数(如 get_mode、get_config),在 `rpc_wifi_*` 返回后再把 portable 结果转回 native。

> **为什么不是 `esp_wifi_weak.c`?** `esp_wifi_weak.c` 是 facade 层,只接触 native 类型,不跨越 portable/native 边界。它的职责是直接转发,不应承担类型转换决策。

> **为什么 `esp_hosted_api_priv.h` 不修改?** 该头文件的声明必须保持 native 签名,因为 `esp_wifi_weak.c` 包含它并按 native 类型调用。转换发生在实现体(`esp_hosted_api.c`)内部,而非接口层面。
