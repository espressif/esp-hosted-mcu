# Host 通用框架完成度评估与后续迁移大纲

> **本文档定位**
>
> 本文档基于当前 Host 通用框架的实际现状，回答以下问题：
>
> - 当前 Host 通用框架距离“真正完整体”还有多远
> - 当前已经形成了哪些基础，哪些部分仍处于过渡态
> - 后续优化和迁移的主方向应该是什么
> - 推进过程中最主要的难点和风险在哪里
>
> 本文档是**现状评估与方向大纲**，不是实现设计文档。
>
> 因此本文档**不展开具体代码细节**，不讨论某个函数如何改、某个文件如何拆、某个接口签名如何设计，也不替代后续的实施计划或代码级设计文档。

## 1. 先给结论

### 1.1 当前总体判断

截至当前阶段，Host 通用框架**还没有达到完整体状态**。

但它也已经明显越过了“只有概念和目录结构”的阶段。

当前更准确的判断是：

1. 通用框架的总体骨架已经建立
2. 基础抽象层已经成形，方向是正确的
3. 部分关键链路已经迁入新框架
4. 但 transport 主链路、兼容层退场、特殊通信路径和真实跨平台闭环仍未收口
5. 因此当前状态应定义为：**结构已建立、关键路径仍在迁移中的过渡态框架**

### 1.2 不能怎么理解

当前状态不能被简单理解为以下任一种：

1. “通用框架已经完成”
2. “现在只差补几个 port 文件”
3. “其实只是把 OS 抽象挪出来了，其他都没变”

这三种理解都不准确。

更合理的表述是：

> Host 通用框架已经完成了第一阶段的基础框架搭建和部分能力迁移，但离真正完整的跨平台 Host 架构仍有明显距离，后续工作的重点应转向关键路径收口，而不是继续停留在局部抽象扩展。

## 2. 什么叫“真正完整的 Host 通用框架”

为了判断当前还差多少，必须先明确“完整体”是什么。

在本项目语境下，所谓“真正完整的 Host 通用框架”，至少应满足以下几个条件。

### 2.1 核心层真正稳定、独立、可复用

完整体下，核心层应具备以下特征：

1. 核心逻辑不再依赖某个既有平台的实现假设
2. 平台差异被限制在清晰的适配边界之内
3. 新平台接入时，核心层不需要反复被平台特性牵引回退

### 2.2 平台差异有清晰收口面

完整体不要求所有平台都已经实现，但要求架构上已经清楚回答：

1. 哪些能力由平台提供
2. 哪些能力由共享层提供
3. 哪些差异可以通过统一抽象表达
4. 哪些差异必须明确标记为平台特例或暂不支持

### 2.3 Transport 不再是“半抽象化”状态

完整体里最关键的一条，是 transport 必须从“概念通用化”进入“运行链路通用化”。

也就是说，不能只是把 transport 名义上纳入统一入口，而实际主路径仍主要依赖旧实现存活。

### 2.4 已声明支持的能力必须口径一致

完整体不要求所有 transport 一步到位，但要求：

1. 已支持的能力有明确完成口径
2. 未支持的能力有明确边界说明
3. 不存在“看起来已纳入统一框架，实际上仍主要依赖旧路径”的长期模糊状态

### 2.5 需要有真实平台证明，而不是只有静态合理性

如果没有至少一个第二平台的真实闭环验证，就不能把“跨平台可落地”当作已被证明的结论。

mock、编译通过、目录分层、局部抽象成立，这些都很重要，但还不足以构成完整体的证据。

## 3. 当前已经形成的基础

虽然还没完成，但当前框架已经具备一些非常明确的正向基础。

这些基础说明当前不是从零开始，而是已经具备继续收口的现实条件。

### 3.1 架构分层已经建立

当前 Host 通用框架已经不再是单层堆叠式实现，而是开始形成：

1. 核心共享层
2. 平台适配层
3. 平台相关配置入口
4. 验证与 mock 支撑层

这说明框架方向已经从“平台绑定式工程代码”转向“共享内核 + 平台适配”的结构。

### 3.2 基础能力抽象已经形成

当前已经能够明显看出，基础能力不再散落在业务代码里，而是围绕以下几类能力形成统一抽象：

1. OSAL
2. Event
3. Transport

这意味着框架已经具备继续向更多平台扩展的架构前提。

### 3.3 初始化链条已经开始统一

当前已经不是由每一层各自零散地初始化，而是开始收敛到统一的初始化组织方式。

这对于后续跨平台接入很重要，因为跨平台问题最容易失控的地方，往往不是单个 API，而是初始化顺序、生命周期和失败回滚边界。

### 3.4 类型层已经开始从平台原生定义中抽离

当前工作已经不只停留在“线程、锁、队列”这种 OS 层能力抽象，而是开始向类型边界推进。

这说明通用化目标已经从“能移植运行”向“能稳定维护和持续演进”迈进了一步。

### 3.5 已经具备非生产平台验证基础

当前已经存在 mock / 非真实硬件环境下的验证基础，这说明新框架并不是完全依赖单一生产环境才能推进。

这对于后续迁移非常关键，因为它允许团队在真实板 bring-up 之前，先把一部分结构性问题提前暴露出来。

## 4. 当前距离完整体的主要差距

如果要问“现在还差多少”，最核心的答案不在数量上，而在链路层级上。

当前的主要差距，集中在下面 4 类问题。

### 4.1 差距 1：主运行链路仍未脱离 legacy 路径

这是当前距离完整体最大的差距，也是最决定性的差距。

从现状看，新框架已经建立了统一的结构入口，但主运行链路仍未完全摆脱旧路径支撑。这里面实际包含三个彼此关联的侧面：

1. transport 数据面尚未完全收口
2. 控制面闭环仍不够彻底
3. 兼容层仍在主路径中承担不可忽略的作用

这三者本质上描述的是同一个问题：

> 新框架已经建立，但还没有彻底成为“可以独立成立的唯一主路径”。

更进一步，从当前驱动层实现看，新 transport contract 还没有真正成为 transport 驱动层的统一运行入口。这说明 legacy 依赖不是局部残留，而是 transport 主链路当前仍然成立的现实基础。

只要这一点不完成，Host 通用框架就还不能称为真正完成。

### 4.2 差距 2：所有 transport 均未完成迁移，SPI-HD 还额外带有协议抽象缺口

从当前代码事实看，SPI、SDIO、UART、SPI Half-Duplex 当前都还没有完成向新框架 transport contract 的迁移。

因此，这里的问题不能理解为“常规 transport 已基本完成，只有 SPI-HD 落后”。

更准确的判断是：

1. 所有 transport 驱动当前都仍显著依赖 legacy 路径
2. SPI Half-Duplex 的“特殊”主要不在于它是唯一未迁移者，而在于它除共性 legacy 依赖外，还额外带有寄存器访问、DMA 流程和数据线协商等协议层复杂度
3. 后续治理应拆成两层：先收口 transport 共性主路径，再专题处理 SPI-HD 的专属协议抽象

### 4.3 差距 3：配置入口与架构口径仍未完全统一

当前的一个明显问题，是“结构上看起来统一”，但“口径上还没有完全收口”。

这类问题的风险在于：

1. 不同人对当前支持范围理解不同
2. 新增平台时会出现入口分裂
3. 某些能力名义上已纳入框架，实际上并未进入统一完成态

### 4.4 差距 4：真实跨平台证明仍不足

当前阶段的结构基础和 mock 基础已经足够说明“这个方向有希望成立”。

但“有希望成立”和“已被证明成立”之间，还差真实平台闭环。

没有第二平台真实 PoC，很多问题仍停留在静态合理性层面，而没有被真实执行环境检验。

### 4.5 当前判断的典型可验证线索

本文档不是代码审计报告，因此不展开逐文件分析；但为了让上述判断具备最小可验证性，这里给出几条典型锚点，供读者自行复核：

1. 在 [../../host/drivers/transport/spi_hd/spi_hd_drv.c](../../host/drivers/transport/spi_hd/spi_hd_drv.c) 这条 SPI Half-Duplex 主路径中，仍可见对 legacy `g_h.funcs` SPI-HD 槽位的直接使用，这说明 SPI-HD 除共性 legacy 依赖外，仍保留专属协议路径。
2. 在 [../../host/core/src/h_serial_if.c](../../host/core/src/h_serial_if.c) 与 [../../host/core/src/h_rpc_core.c](../../host/core/src/h_rpc_core.c) 所代表的控制面路径中，一方面仍有对 `transport_pserial_*` 的直接调用，另一方面也保留了经由 `h_serial_if_*` 对同一路径的桥接封装，这说明控制面对 legacy 的耦合同步存在“直接调用”和“间接桥接”两层。
3. 在 [../../host/core/src/h_transport_drv.c](../../host/core/src/h_transport_drv.c) 中，SPI-HD 相关编译期分支内部仍要进行运行时数据线协商；而这条协商路径会经由 [../../host/port/include/h_wrapper.h](../../host/port/include/h_wrapper.h) 和 [../../host/port/esp-idf/h_osal.c](../../host/port/esp-idf/h_osal.c) 下沉到 port-specific SPI-HD 扩展实现。这说明它不是简单“遗留痕迹”，而是当前 transport 协商逻辑的一部分。
4. 在 [../../host/drivers/transport/transport_drv.c](../../host/drivers/transport/transport_drv.c) 这个 legacy transport orchestrator 中，重启、定时器、内存拷贝和对象分配等基础动作仍直接经由 `g_h.funcs` 完成。这说明 legacy 依赖不仅存在于单个叶子驱动文件，还进入了 transport 主链路的编排层。
5. 从 [../../host/drivers/transport/spi/spi_drv.c](../../host/drivers/transport/spi/spi_drv.c)、[../../host/drivers/transport/sdio/sdio_drv.c](../../host/drivers/transport/sdio/sdio_drv.c)、[../../host/drivers/transport/uart/uart_drv.c](../../host/drivers/transport/uart/uart_drv.c) 的当前形态看，驱动层仍主要经由 legacy `_h_*` 槽位运行，尚未通过 `h_spi_transfer`、`h_sdio_read_block`、`h_uart_read` 等新 wrapper 入口形成统一 transport contract 主路径。

这些线索的意义不在于展开实现细节，而在于说明：本文所说的“未收口”并不是抽象担忧，而是可以从当前代码结构中被直接观察到的事实。

## 5. 当前最主要的难点分析

如果后续要继续推进，真正难的并不是“再抽象几个接口”，而是以下几类结构性难点。

### 5.1 难点 1：Transport 不是单一总线问题，而是组合问题

transport 看起来像是一个总线抽象问题，但在真实系统里，它通常同时牵涉：

1. 总线能力
2. GPIO
3. 中断
4. 缓冲区管理
5. DMA / 对齐 / 时序
6. 控制面和数据面的协同

因此 transport 的迁移难度天然高于 OSAL 和事件层。

### 5.2 难点 2：新旧并存期很容易变成长尾状态

迁移过程中，新旧并存本来是合理的。

但如果没有明确的退场原则，新旧并存会逐步演变成：

1. 新框架负责描述结构
2. 旧实现负责真正跑通

一旦形成这种长期格局，通用框架就会停留在“看起来完成、实则未完成”的状态。

### 5.3 难点 3：协议特殊 transport 往往最容易长期挂起

这里的“特殊”，指像 SPI Half-Duplex 这样除共性 transport 迁移外，还额外带有协议层抽象负担的路径，而不代表其他 transport 已经完成迁移。

这类 transport 的复杂度、差异性和验证成本通常都更高。

它们最容易被放到“以后再说”，但架构完成度往往恰恰会被它们拖住。

因此后续必须明确：

1. 哪些能力属于完整体必须覆盖
2. 哪些能力属于阶段性可延后项
3. 哪些能力必须单独作为专题收口

### 5.4 难点 4：真实平台验证会暴露与 mock 完全不同的问题

mock 擅长发现：

1. 抽象边界错误
2. 初始化组织问题
3. 线程和事件语义问题
4. 基础接口契约不匹配

真实硬件则更容易暴露：

1. 时序问题
2. 中断问题
3. GPIO 电平语义问题
4. 缓冲区和对齐问题
5. 总线与控制面的耦合问题

因此后续迁移不能把 mock 成功直接等同于真实平台无风险。

### 5.5 难点 5：最难的不是技术点，而是完成口径

如果团队对“什么叫完成”没有统一口径，那么后续任何阶段都可能出现以下偏差：

1. 有人按目录判断完成
2. 有人按编译通过判断完成
3. 有人按 mock 成功判断完成
4. 有人按第二平台成功判断完成

口径不统一，迁移就会反复争论状态，而不是推进真实收口。

## 6. 后续优化方向

基于当前现状，后续优化方向应当聚焦于“关键路径收口”，而不是继续平铺式扩展。

### 6.1 方向 1：先统一完成态定义

后续第一件事，不是先改代码，而是先统一口径。

需要明确：

1. 第一阶段完成意味着什么
2. 真正完整体意味着什么
3. 哪些属于阶段性允许保留的兼容项
4. 哪些属于不能继续新增的历史包袱

### 6.2 方向 2：优先收口 transport 主链路

后续优化的主轴不应再放在零散抽象，而应放在 transport 主路径是否真正进入新框架。

只有 transport 收口，通用框架才会从“结构成立”走向“运行成立”。

### 6.3 方向 3：补足控制面独立闭环

控制面必须成为新框架下的最小独立生命线。

这件事的重要性不亚于 transport，因为它决定了新框架是否能真正摆脱旧桥接路径生存。

### 6.4 方向 4：把协议特殊 transport 单独作为专题治理

这里的“协议特殊”，指像 SPI Half-Duplex 这样，除共性 transport 收口之外，还附带寄存器、DMA、数据线协商等额外协议抽象负担的路径。

不建议把这类 transport 混在常规收口里顺手做完。

更合理的方式是把它们作为单独专题，明确：

1. 目标口径
2. 阶段目标
3. 风险边界
4. 完成定义

### 6.5 方向 5：逐步压缩兼容层主路径依赖

后续优化的重要方向之一，不是立刻删除旧代码，而是逐步降低旧依赖在新主路径中的必要性。

只要这条趋势是持续的，迁移就是在前进；

如果相反，新功能仍继续加深对旧兼容层的依赖，迁移就会开始倒退。

### 6.6 方向 6：尽快形成第二平台真实闭环

后续不能无限停留在“框架看起来已经合理”。

必须尽快把至少一个第二平台的真实 PoC 建起来，用真实 bring-up 去验证：

1. 抽象是否足够
2. 边界是否清晰
3. 风险是否可控
4. 迁移成本是否符合预期

### 6.7 方向 7：最终通过验证体系和文档口径收尾

真正的收尾不是“代码差不多了”，而是：

1. 有统一的完成度定义
2. 有稳定的验证路径
3. 有跨平台落地证据
4. 有清晰的兼容层退场原则

只有这样，Host 通用框架才算进入可维护、可扩展、可对外表述的稳定阶段。

## 7. 建议的后续迁移大纲

下面给出的是方向性迁移大纲，而不是实现方案。

### 阶段 0：统一现状口径

目标：统一团队对当前阶段的判断。

本阶段重点不是实现，而是共识：

1. 当前不是完成态
2. 当前不是只有 OS 抽象迁移
3. 当前处于关键路径待收口的中段迁移阶段

收敛标准：

1. 团队对当前状态的表述不再出现明显分歧
2. “已完成什么、未完成什么”形成统一口径
3. 后续工作不再建立在“已经基本完成”的错误前提上

### 阶段 1：统一边界与完成定义

目标：先把“什么是完整体”说清楚。

本阶段应形成：

1. 完成态判断标准
2. 分阶段目标定义
3. 兼容层保留与退场口径
4. 协议特殊 transport 的阶段归属

收敛标准：

1. 团队明确知道哪些目标属于“完整体必须具备”
2. 各 transport 的状态口径一致
3. 兼容层从“长期模糊存在”转为“有边界的阶段性存在”

### 阶段 2：收口通用 transport 主路径

目标：先让至少一类通用 transport 真正进入新框架的主运行链。

这一阶段是整个后续工作的中轴。

如果这一阶段没有完成，后续第二平台验证和完整体判断都会缺少根基。

收敛标准：

1. 至少一条通用 transport 已能在新框架主路径上独立成立
2. 该类通用 transport 的核心读写、生命周期与中断协同不再主要依赖 legacy 路径兜底
3. 团队能够明确区分“通用基线已收口的路径”和“仍属过渡路径”

### 阶段 3：收口控制面独立性

目标：让新框架下的控制面具备独立成立能力。

这是架构从“概念通用化”进入“运行通用化”的关键步骤之一。

收敛标准：

1. 控制面不再依赖旧桥接路径才能完成基本闭环
2. 新框架具备最小独立生命线
3. 控制面与 transport 主路径的关系清晰、稳定

### 阶段 4：专题处理协议特殊 transport

目标：把 SPI Half-Duplex 这类除共性迁移外还携带专属协议层的 transport 明确纳入专题收口计划，而不是长期挂起。

本阶段更适合做成专题治理，而不是顺手补丁式推进。

收敛标准：

1. 协议特殊 transport 的额外协议层目标口径被单独定义
2. 它不再混在通用 transport 基线完成度里造成认知混乱
3. 团队能明确回答“共性迁移完成到哪里、专属协议抽象还差什么”

### 阶段 5：推进第二平台真实 PoC

目标：把当前框架从“静态上合理”推进到“真实平台上成立”。

第二平台真实 PoC 不是附属项，而是判断完整体是否成立的决定性证据之一。

收敛标准：

1. 至少一个第二平台完成最小控制面闭环
2. 至少一个第二平台完成最小数据面验证
3. 团队能够基于真实结果判断 contract 是否足够、边界是否合理

### 阶段 6：收口验证体系与对外口径

目标：让框架完成度有稳定表达，而不是继续依赖口头判断。

这个阶段应关注：

1. 验证闭环
2. 文档口径
3. CI 策略
4. 兼容层退场节奏

收敛标准：

1. 完成度判断不再依赖口头解释
2. 对外口径、内部口径与验证结果一致
3. 兼容层退出不再只是愿景，而有实际节奏安排

## 8. 当前阶段最应该坚持的原则

在后续推进中，建议坚持以下原则。

### 8.1 原则 1：优先解决决定性差距

当前最决定框架完成度的，不是更多抽象点，而是关键路径是否真正收口。

### 8.2 原则 2：不再制造新的长期兼容债务

迁移期允许有兼容层，但不应继续扩大兼容层的战略地位。

### 8.3 原则 3：不把阶段成果误叫成最终完成

当前已有成果应被承认，但也不应被过度表述。

### 8.4 原则 4：先证明主路径，再扩展特性

在关键链路未完成前，不建议把精力过多分散到外围扩展特性的等价迁移上。

### 8.5 原则 5：真实平台验证必须尽早进入计划核心

越晚做第二平台验证，越容易把结构性问题拖成长尾问题。

## 9. 最终建议

### 9.1 当前最准确的阶段定义

建议把当前 Host 通用框架定义为：

> **第一阶段基础框架已经建立，但距离真正完整体仍有清晰差距，当前的核心任务是关键路径收口，而不是继续扩展抽象表面。**

### 9.2 当前最关键的下一步

如果只抓一件事，建议优先抓：

> **让通用框架的主 transport 路径真正独立成立，并以此为基础推进第二平台真实闭环。**

### 9.3 本文档的使用方式

本文档用于：

1. 统一团队对当前完成度的判断
2. 统一后续迁移优先级
3. 明确当前真正的难点集中在哪些方向

本文档不用于：

1. 指定具体文件改法
2. 指定函数级实现策略
3. 展开接口级设计细节

如果后续需要进入实施层，应在此文档基础上另行拆出：

1. 任务化实施计划
2. transport 专题方案
3. 第二平台 PoC 计划
4. 兼容层退场计划
