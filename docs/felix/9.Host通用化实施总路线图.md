## 总体目标

把当前 Host 通用框架从「部分满足跨平台移植友好型」提升到「完整框架对平台适配者足够稳定和透明」的终态,即 8 号评审中"是否满足跨平台移植友好型"四个维度全部为「是」:

1. 移植入口清晰 — 已是
2. 平台能力有统一契约 — 已是
3. 核心公共类型彻底独立于原平台 — **本路线图待解决**
4. 完整主路径已被非原生平台验证 — **本路线图待解决**

完成后(指**全部 5 个门槛包括第二平台 PoC 完成**,即里程碑 D)应能放心使用以下对外表述:

> Host 通用框架已完成跨平台移植友好型收口,新增平台只需实现 port contract 即可,核心层不再需要平台专属改动。

这个口径**不允许**在里程碑 D 之前使用 — "新增平台只需实现 port contract 即可" 这个判断本身就需要门槛 5 来证伪。在里程碑 C 完成而门槛 5 未完成时,只能使用更弱的口径,见后文"推进顺序与里程碑"段。

## 三个口径的明确定义

为避免后续讨论再绕"什么算 portable / 什么算 testable"这种语义争议,本路线图采用以下定义,门槛 1 的工作之一就是把它们落到脚本和文档里:

| 口径 | 定义 | 当前覆盖文件数 / `host/core/src/` 总数 |
|---|---|---|
| **portable**(可移植) | 通过 `check_core_isolation.sh` 隔离检查,即不依赖 `port_esp_hosted_host_*`、`ESP_LOG*`、`esp_*` 头文件、FreeRTOS 直接调用、`heap_caps_*`、`__attribute__((constructor))` 等平台专属符号 | 4/14 |
| **testable**(可被非 ESP 平台验证) | 被 `run_linux_mock_tests.sh` 持续编译且测试用例真实执行其**生产代码路径**(不依赖 `H_BUILD_TESTS` 测试专用分支) | 真实生产路径覆盖 ≤ 3/14 |
| **已验证生产路径** | 同时满足 portable 和 testable,即"声明可移植"且"被 mock 持续验证生产路径" | 3/14 |

终态目标:三个口径**完全重合**,且都达到 14/14。

## 门槛全览

### 门槛 1:完成度口径统一

**目标:** 把 portable / testable / 已验证生产路径三个集合显式落到脚本、目录命名、文档,使三者对齐,后续工作有统一的衡量基线。

**工作包(WP):**

- WP 1.1 在 `scripts/check_core_isolation.sh` 顶部注释和 `scripts/run_linux_mock_tests.sh` 顶部注释中各自明确"本脚本验证哪个口径"
- WP 1.2 在两个脚本里以注释或显式变量方式输出"当前口径下的文件清单 + 比例"
- WP 1.3 把 `h_api.c` 加入 Linux mock 编译,与其 portable 声明对齐;或反之,如果 mock 暂不需要 h_api.c,则在 portable 集合的脚本注释里说明原因
- WP 1.4 把 `h_rpc_core.c` 在 mock 编译里走的 `H_BUILD_TESTS` 测试专用分支显式标注 — 要么列入"已知不计入生产路径覆盖",要么改造让生产路径在 mock 也可走通
- WP 1.5 在 8 号文档或新增简短附录里固化上述定义,作为后续门槛验收依据

**验收口径:**

- `scripts/check_core_isolation.sh` 输出一行明确口径声明 + 文件清单
- `scripts/run_linux_mock_tests.sh` 输出一行明确口径声明 + 文件清单
- 两份文件清单在文档(8 号 + 本文档)中列出,且与脚本完全一致
- `h_api.c` / `h_rpc_core.c` 的特殊处理有显式说明

**依赖:** 无

**风险:** 低。本质是文档+脚本注释级改动,没有深度代码改造。

**估算:** S(0.5–1 天)

**对应 step 级 plan:** `10.门槛1-完成度口径统一-实施计划.md`(待写,先做先开)

### 门槛 2:公共类型收口

**目标:** `host/core/include/h_public/h_wifi_types.h` 不再通过 `ESP_PLATFORM` 直通 typedef 到 ESP-IDF 原生 `wifi_*` 类型;核心层始终对外暴露统一的 `h_wifi_*` 类型;ESP-IDF 端通过 port 层完成 native ↔ portable 的转换。

**工作包:**

- WP 2.1 删除 `h_wifi_types.h` 中 `#ifdef ESP_PLATFORM` 直通分支,使所有平台都使用 portable struct 定义
- WP 2.2 在 `host/port/esp-idf/` 下新建 `h_wifi_type_adapt.c/h`(或同等位置),提供 `h_wifi_*` ↔ ESP-IDF native `wifi_*` 的双向字段映射函数
- WP 2.3 改造 RPC 路径上所有原本依赖"`h_wifi_*` 等同于 `wifi_*`"的代码点(主要在 `h_rpc_req.c` / `h_rpc_evt.c` / `h_rpc_wrap.c` / `h_rpc_wrap_api.c`),改为显式调用 type adapter
- WP 2.4 为关键 `h_wifi_*` 类型添加编译期布局一致性断言(`_Static_assert` + `offsetof` + `sizeof`),覆盖 `h_wifi_init_config_t` / `h_wifi_config_t` / `h_wifi_scan_config_t` / `h_wifi_ap_record_t` 等。当 ESP-IDF 端启用 zero-copy 时由这些断言守住布局兼容
- WP 2.5 在 `check_core_isolation.sh` 中**移除** `h_wifi_types.h` 的 ESP-IDF 直通白名单条目(line 27–28)
- WP 2.6 跑全套测试 + ESP-IDF 端编译验证,确保 RPC 路径行为不退化

**验收口径:**

- `h_wifi_types.h` 在所有平台下都暴露同一份 portable struct 定义,不再有 `ESP_PLATFORM` 分支
- ESP-IDF port 下 RPC 路径行为(scan / connect / get_ap_records 等)与改动前一致
- 至少 4 个关键类型有 `_Static_assert` 防 drift
- `check_core_isolation.sh` 不再需要 `h_wifi_types.h` 的特殊豁免

**依赖:** 建议在门槛 1 完成后启动,以便用统一口径衡量进展。但二者实际可并行(口径属文档+脚本层,类型属代码层,改动面不重叠)。

**风险:**

- 中–高。RPC 路径上 `wifi_config_t` 的字段引用点较多,若 type adapter 漏覆盖,会出现运行期字段错位
- ESP-IDF 升级后字段变化可能让 `_Static_assert` 失败 — 这是预期效果,但需要文档说明如何处置
- 缓解:WP 2.4 的断言是关键防线,WP 2.6 的回归测试要覆盖至少 STA 连接、AP 启动、扫描三条主路径

**估算:** M–L(1–2 周)

**对应 step 级 plan:** `11.门槛2-公共类型收口-实施计划.md`(待写,门槛 1 完成后启动)

### 门槛 3:核心目录收口

**目标:** `host/core/src/` 下所有主路径文件通过统一 isolation 检查,不再依赖 `port_esp_hosted_host_*` 头文件、`ESP_LOG*` 宏和旧平台专属符号。`check_core_isolation.sh` 的 `PHASE1_SCOPE` 扩展到覆盖整个 `host/core/src/`。

**工作包:**

涉及的 10 个核心 src 文件按文件归属与实际改动面分组(不再使用"简单/中等/复杂"标签 — 容易低估单文件深度依赖):

- WP 3.1 **小工具组**:`h_rpc_utils.c`(98 行)、`h_rpc_slave_if.c`(265 行)、`h_transport_util.c`(33 行)
  - 替换 `ESP_LOG*` → 移植层日志接口(若不存在则在 port contract 里先定义 `H_LOG*` 宏)
  - 替换 `port_esp_hosted_host_log.h` / `port_esp_hosted_host_os.h` 等 include
  - `h_transport_util.c` 涉及 DMA 内存接口(`h_malloc_align`、`HOSTED_MEM_CAP_DMA`)需走契约
- WP 3.2 **Transport Driver(独立大块)**:`h_transport_drv.c`(955 行)
  - 这一文件单独成组,因为远不止日志替换
  - 替换 legacy transport 头(`transport_drv.h`、`esp_hosted_transport*.h`、`stats.h`、`hci_drv.h`)为通用契约
  - `struct esp_priv_event` 等 ESP-private 结构体需移到核心层私有头或通过 port 契约提供
  - power-save 路径(`esp_hosted_power_save_init()` 之类)从核心实现解耦,改成通过 port 契约的可选钩子
  - 排查 `ESP_PRIV_FIRMWARE_CHIP_*`、`chip_type` 等 ESP-private 符号并去掉
- WP 3.3 **RPC 请求/响应/事件**:`h_rpc_req.c`、`h_rpc_rsp.c`、`h_rpc_evt.c`
  - 日志替换同 WP 3.1
  - `port_esp_hosted_host_config.h` / `port_esp_hosted_host_os.h` 依赖换成 `host/port/include/` 下契约头
  - 排查 `esp_event_*`、`esp_timer_*` 直接调用并改为契约调用
  - 强依赖门槛 2 的 type adapter — 这三个文件大量引用 `wifi_*_t`
- WP 3.4 **RPC Core/Wrap 三件套**:`h_rpc_core.c`、`h_rpc_wrap.c`、`h_rpc_wrap_api.c`
  - RPC 核心深度实现
  - 排查 GCC 扩展、`__attribute__((constructor))` 等并改造
  - 需要先确认 WP 3.2 + WP 3.3 已稳定
- WP 3.5 扩展 isolation 脚本:`scripts/check_core_isolation.sh` 的 `PHASE1_SCOPE` 扩到覆盖 `host/core/src/*.c`,且改名去掉 "Phase 1" 这种阶段性命名(改成 `CORE_PORTABLE_SCOPE` 之类)
- WP 3.6 跑 ESP-IDF 端全套构建 + 真实硬件冒烟测试(`scripts/hw_smoke_test.sh`),确保去 ESP 化没有引入回归

**验收口径:**

- `host/core/src/` 下所有 `.c` 文件通过 isolation 检查
- ESP-IDF 端编译通过,真实硬件冒烟测试通过(STA 连接、扫描、断开)
- isolation 脚本注释和变量名里不再出现 "Phase 1" 这种阶段性表述

**依赖:**

- 强依赖门槛 2 — 类型未收口,RPC 路径里的 `wifi_*_t` 引用没法去 ESP
- 内部:WP 3.1 → WP 3.2 → WP 3.3 → WP 3.4 是递进顺序,WP 3.5 + WP 3.6 是最后的统一收口

**风险:**

- 高。10 个文件覆盖控制面、事件、传输三大主路径,且 `h_transport_drv.c` 单文件 955 行 + power-save / private event 等深度耦合,任何一处 OS 抽象不充分都会暴露
- 缓解:门槛 1 的口径统一已让 mock 测试有清晰增量验收;每完成一个 WP 就把对应文件加入 mock 编译,缩短反馈环

**估算:** L+(4–6 周) — WP 3.2 单独占大块,过去归为"简单组"的判断系统性低估了它

**对应 step 级 plan:** `12.门槛3-核心目录收口-实施计划.md`(待写,门槛 2 完成后启动)

### 门槛 4:Linux mock 覆盖扩展

**目标:** `run_linux_mock_tests.sh` 持续编译并测试 `host/core/src/` 下全部主路径文件,使"已验证生产路径"集合覆盖整个 `host/core/`。

**工作包:**

- WP 4.1 把门槛 3 已收口的 RPC 文件(`h_rpc_req.c`、`h_rpc_rsp.c`、`h_rpc_evt.c`、`h_rpc_wrap.c` 等)加入 `CORE_SRCS`
- WP 4.2 把传输工具(`h_transport_util.c`、`h_transport_drv.c`)加入 `CORE_SRCS`
- WP 4.3 在 `host/port/linux/src/` 下补充对应的 mock symbol 和 stub 实现(transport mock 已有,需要扩展)
- WP 4.4 在 `tests/` 下增补针对 RPC 请求/响应/事件路径的测试用例,覆盖正常 + 错误 + 边界场景
- WP 4.5 取消 `h_rpc_core.c` 的 `H_BUILD_TESTS` 测试专用分支(若仍存在),让生产代码路径直接被测试覆盖
- WP 4.6 mock 编译开启 ASAN + UBSAN + TSAN 三个 sanitizer 跑通

**验收口径:**

- `run_linux_mock_tests.sh` 的 `CORE_SRCS` 与 `host/core/src/*.c` 完全一致
- portable / testable / 已验证生产路径三个集合显式重合,均达到 14/14
- 三个 sanitizer 全部通过,无新增警告

**依赖:** 强依赖门槛 3。门槛 3 进行中即可滚动纳入(每收口一组就纳入一组),不必等 3 全部完成。

**风险:**

- 中。Mock 实现的充分性可能在加新文件时暴露不足(如某个 RPC 路径调了一个未 stub 的 OS 接口)
- 缓解:WP 4.3 的 mock 补充应跟随 WP 4.1/4.2 同步推进

**估算:** M(3–5 天,与门槛 3 并行推进可压缩到 1–2 天净增)

**对应 step 级 plan:** `13.门槛4-mock覆盖扩展-实施计划.md`(待写,可与门槛 3 后期并行启动)

### 门槛 5:第二平台 PoC

**目标:** 除 ESP-IDF 与 Linux mock 外,在**第三个真实硬件平台**上完成最小 bring-up,验证 port contract 在真实总线/IRQ/DMA 等硬件相关维度上的充分性。本路线图推荐 **Zephyr 作为 RTOS 选择**,目标硬件可在 nRF52(SPI 已成熟)或 STM32(SDIO 可选)中择一。

> **重要:** native_posix 等模拟器**不计入**门槛 5 验收。原因:它没有真实 SPI / SDIO / UART 总线,仅能验证 OSAL + event 子集,而 port contract 中真正需要被检验的就是 transport 这一块 — 用模拟器代替真实板会让本门槛失去自身存在的意义。native_posix 仅作为 WP 5.3 的中间集成产物使用。

**工作包:**

- WP 5.1 选定**真实硬件**与 RTOS 组合(推荐:Zephyr + nRF52 SPI,或 Zephyr + STM32 SDIO;具体型号到 14 号 step plan 再定)。同时确认 ESP 协处理器侧硬件连线方案
- WP 5.2 在 `host/port/zephyr/`(新建目录)下实现 port contract 的最小集合:OSAL、event、transport(至少 SPI 一种,且必须是真实总线驱动)
- WP 5.3(中间产物,不计入验收) 用 Zephyr native_posix 跑 OSAL + event 子集集成测试,提前暴露非 transport 路径的 port 缺口
- WP 5.4 在真实板上集成 `host/core/`,跑通 hello-world 级控制面 RPC(如 `h_wifi_init` → 收到响应),确认 transport 真实总线、IRQ、DMA 路径打通
- WP 5.5 在真实板上跑通 STA 连接全流程(扫描 → 连接 → 拿到 IP 或对等事件) — **这是门槛 5 的硬验收**
- WP 5.6 把 PoC 结果归档:port contract 中哪些接口"够用"、哪些"勉强够用"、哪些"显然不够"。形成"port contract 充分性评估报告"
- WP 5.7 基于 PoC 结论,决定 transport contract 是否需要拆成 bus contract / board-irq contract / netif contract(8 号文档问题 4 的"再评估项")

**验收口径(必须全部满足):**

- 至少一块**真实硬件**(非模拟器)跑通 STA 连接全流程
- 形成"port contract 充分性评估报告"并归档
- 报告输出 transport contract 是否需要拆分的明确结论

**依赖:** 强依赖门槛 1–4 全部完成。否则 PoC 是在不稳定边界上做兜底,而不是验证通用框架本身。

**风险:**

- 高,且不确定性大。Zephyr 的 SPI / SDIO 驱动模型与 ESP-IDF 差异较大;PoC 可能暴露 transport contract 抽象不足。硬件供应、走线、与 ESP 协处理器对接也都是不确定性来源
- 缓解:WP 5.6 把"暴露的不足"作为正向产出而不是失败 — 它正是这次 PoC 的核心价值。WP 5.3 的 native_posix 中间集成可以提前清理非 transport 的 port 问题,把真实板调试聚焦在硬件相关问题上

**估算:** L(1–3 周,取决于 Zephyr 经验和目标硬件可用性。若硬件 / 走线 / 对接需新做,可能继续上调)

**对应 step 级 plan:** `14.门槛5-第二平台PoC-实施计划.md`(待写,门槛 4 完成后启动)

## 推进顺序与里程碑

按单开发者节奏建议如下里程碑:

### 里程碑 A:口径稳定(预计 0.5–1 天)

完成门槛 1。在此节点之后,所有"完成度"讨论都有统一依据。

### 里程碑 B:类型主权回收(预计 1–2 周)

完成门槛 2。在此节点之后,公共 API 的语义来源完全在核心层,ESP-IDF 升级不再影响公共接口含义。

### 里程碑 C:核心目录收口 / v0.9 阶段性可用(预计 4–6 周)

门槛 3 完成,门槛 4 在该里程碑结束时一并完成。在此节点之后:

- `host/core/src/` 全部通过 isolation 检查
- `run_linux_mock_tests.sh` 覆盖整个 `host/core/`

## 退出条件 / 项目级"完成"定义
