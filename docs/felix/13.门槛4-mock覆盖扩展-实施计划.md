## 2. 根因定位（为什么现在停在 5/13）

### 2.1 控制性阻塞不是 `.c` 文件本身，而是旧头文件链

当前 mock 编译被两条老头链卡住：

```text
h_rpc_req.c / h_rpc_rsp.c / h_rpc_evt.c / h_rpc_utils.c
		-> rpc_core.h
		-> transport_drv.h
		-> port_esp_hosted_host_config.h / port_esp_hosted_host_log.h / port_esp_hosted_host_spi*.h ...

h_rpc_wrap.c / h_transport_drv.c
		-> transport_drv.h
		-> esp_err.h + port_esp_hosted_host_config.h + transport 专属 port 头
```

### 2.2 已确认的头链证据

`host/drivers/transport/transport_drv.h` 当前仍直接包含：

- `esp_err.h`
- `port_esp_hosted_host_config.h`
- `port_esp_hosted_host_spi.h`
- `port_esp_hosted_host_sdio.h`
- `port_esp_hosted_host_spi_hd.h`
- `port_esp_hosted_host_uart.h`

并仍暴露旧宏：

- `SUCCESS` / `FAILURE`
- `H_DEFLT_FREE_FUNC g_h.funcs->_h_free`

`host/drivers/rpc/core/rpc_core.h` 当前仍直接包含：

- `transport_drv.h`
- `port_esp_hosted_host_log.h`
- `port_esp_hosted_host_config.h`

因此即使 `.c` 文件已经完成门槛 3 的 portable 收口，只要 mock 编译还经过这些旧头，生产路径就会在进入编译器之前被 ESP-IDF/port 依赖拦住。

### 2.3 `h_rpc_core.c` 的当前测试仍是“旁路测试”

`host/core/src/h_rpc_core.c` 仍以：

```c
#ifdef H_BUILD_TESTS
```

在文件顶部切到一条简化实现路径。当前 `tests/test_rpc_core.c` 测到的是 `h_serial_if_send/recv` 这条轻量分支，不是生产版的：

- queue / semaphore 协调
- async callback 表
- sync response 唤醒
- timer 超时清理
- rx/tx 线程启动与退出

因此门槛 4 的硬问题是：**让 mock 直接覆盖生产路径，而不是继续测试一条“为了测而存在”的替身分支。**

---

## 3. 总体策略（门槛 4 的收口路线）

门槛 4 按以下顺序推进，避免一次性把 7 个文件全塞进脚本后失去定位能力：

1. 先固化脚本中的三桶口径：已验证、持续编译、待纳入。
2. 先拆头链，再纳文件。
3. 先纳入 RPC 叶子文件，再纳 `h_transport_drv.c` 与 `h_rpc_wrap.c` 这两个深水区。
4. 最后取消 `h_rpc_core.c` 的 `H_BUILD_TESTS`，让测试完全回到生产实现。
5. 收尾时统一 sanitizer 与 CI，不另开第二套脚本。

关键原则：

- **优先修真实头链**，不要无限扩张 `tests/stubs/` 去模拟整个旧 port 世界。
- **stubs 只补外部边界**，例如 `esp_err.h`、`sdkconfig.h`、编译期 feature 宏、极少量链接桩。
- **mock 目标是验证生产路径**，不是制造另一套“只在 Linux 下能过”的平行实现。

## 4. WP 4.1 — 固化脚本口径与差集检查

### 4.1 目标

在动代码前，先让 `scripts/run_linux_mock_tests.sh` 能机械表达当前状态与剩余差集，避免门槛 4 中后段出现“脚本过了，但文档口径没对齐”的重复返工。

### 4.2 涉及文件

- `scripts/run_linux_mock_tests.sh`
- `docs/felix/9.Host通用化实施总路线图.md`（如门槛 4 收尾时需同步当前口径）
- `.github/workflows/host-core-test.yml`（仅在脚本口径调整后更新注释/命名）

### 4.3 具体改法

#### Step 1：显式维护三桶集合

脚本中至少保留以下三个集合：

- `MOCK_BUILD_CORE`：当前能进入 Linux mock 持续编译的集合
- `TESTABLE_CORE`：真实走生产路径的集合
- `PENDING_CORE`：portable 已完成但尚未进入 mock 的集合

门槛 4 期间允许三个集合暂时不重合，但必须**显式列出差集**，而不是只在注释里口头说明。

#### Step 2：增加集合差分检查

建议在脚本前半段加入集合对比：

```bash
ALL_CORE_SRCS=$(find host/core/src -maxdepth 1 -name 'h_*.c' | sort)

printf '%s
' "${MOCK_BUILD_CORE[@]}" | sort > build/mock_build_core.txt
printf '%s
' "${TESTABLE_CORE[@]}" | sort > build/testable_core.txt
printf '%s
' "${PENDING_CORE[@]}" | sort > build/pending_core.txt
printf '%s
' "$ALL_CORE_SRCS" > build/all_core.txt

comm -23 build/all_core.txt build/mock_build_core.txt
```

目的不是在门槛 4 初期就强制差集为空，而是让差集变成脚本可见输出。

#### Step 3：门槛 4 完成时收敛为 13/13

门槛 4 完成后脚本应满足：

- `CORE_SRCS` = `host/core/src/*.c` 全集
- `MOCK_BUILD_CORE` = 13/13
- `TESTABLE_CORE` = 13/13
- `PENDING_CORE` 为空

### 4.4 验证

```bash
bash scripts/run_linux_mock_tests.sh

grep -n 'MOCK_BUILD_CORE\|TESTABLE_CORE\|PENDING_CORE' scripts/run_linux_mock_tests.sh

find host/core/src -maxdepth 1 -name 'h_*.c' | sort
```

### 4.5 已知陷阱

1. 不要在门槛 4 中途把 `CORE_SRCS` 一次性改成 13/13，再靠大量 `#ifdef`/stub 去硬顶，这会让定位回归点变得极差。
2. `.github/workflows/host-core-test.yml` 现在仍写着 “current portable/testable subset”，门槛 4 收尾时必须同步更新注释，避免 CI 注释落后于脚本现实。

## 5. WP 4.2 — 解耦旧头文件系统（`transport_drv.h` / `rpc_core.h`）

### 5.1 目标

把当前阻塞 mock 编译的两条旧头链拆开，使 `host/core/src/` 的生产实现可以在不依赖 `port_esp_hosted_host_*` 头文件的情况下被 gcc 直接编译。

### 5.2 涉及文件

- `host/drivers/transport/transport_drv.h`
- `host/drivers/rpc/core/rpc_core.h`
- `host/core/include/h_internal/h_transport_drv.h`
- `host/port/include/h_wrapper.h`
- `host/port/include/h_config.h`
- 视拆分方案而定：新增一份 core-facing internal header 和一份 transport/port private header

### 5.3 具体改法

#### Step 1：`transport_drv.h` 只保留 core 需要的 portable 声明

当前 `transport_drv.h` 同时承担了三种角色：

1. core-facing 类型与函数声明
2. bus/port 专属头引入点
3. 旧时代宏容器（`SUCCESS` / `FAILURE` / `H_DEFLT_FREE_FUNC`）

门槛 4 需要把这三者拆开。

最低要求：

- 把 `port_esp_hosted_host_spi*.h` / `sdio` / `uart` 这些 transport port 头移出 core-facing 头文件
- 把 `esp_err_t` 暴露点收束为 `h_err_t` 或内部别名
- 把 `H_DEFLT_FREE_FUNC` 彻底移除，统一由 `h_free_fn` 提供
- 把 `SUCCESS` / `FAILURE` 这类旧宏清退到 `H_OK` / `H_FAIL`

建议方案：

- 保留一份 **core-facing internal header**：仅放 `transport_channel_t`、`interface_buffer_handle_t`、`esp_hosted_tx()`、`setup_transport()`、`teardown_transport()` 等 core 真实需要的声明
- 新增或保留一份 **driver-private header**：仅供 transport 实现文件包含 bus/port 专属头

#### Step 2：`rpc_core.h` 不再直接引入 port 头

`rpc_core.h` 当前最大的副作用，是它把 `transport_drv.h` 和 `port_esp_hosted_host_*` 一起拖进来，导致 `h_rpc_req.c`、`h_rpc_rsp.c`、`h_rpc_evt.c`、`h_rpc_utils.c` 这些原本已经 portable 的 `.c` 无法直接在 mock 下编译生产路径。

门槛 4 中应完成：

- `#include "port_esp_hosted_host_log.h"` 删除
- `#include "port_esp_hosted_host_config.h"` 删除
- 宏内部的 `HOSTED_FREE` / `ESP_LOGE` 改为 `h_free` / `H_LOGE`
- 仅保留 RPC 相关类型、宏和函数声明，不再承担 port 配置分发职责

#### Step 3：不要把项目公共协议类型误当成 mock 需要 stub 的东西

以下内容应继续来自真实项目头，不应在 `tests/stubs/` 里重造：

- `esp_hosted_transport.h` 里的协议结构
- `ESP_PRIV_*` 协议常量
- protobuf 生成头

换言之，门槛 4 要 stub 的是**平台/外部边界**，不是项目自己的 wire format。

### 5.4 验证

```bash
grep -n 'port_esp_hosted_host_' host/drivers/transport/transport_drv.h host/drivers/rpc/core/rpc_core.h || echo Clean

grep -n 'g_h\.funcs\|ESP_LOG' host/drivers/transport/transport_drv.h host/drivers/rpc/core/rpc_core.h || echo Clean

bash scripts/run_linux_mock_tests.sh
```

### 5.5 已知陷阱

1. 不要为了让 mock 过编译，就把 transport port 头简单地挪到 `tests/stubs/` 同名覆盖；那只是在复制旧结构，而不是清理它。
2. `transport_drv.h` 既被 core 用，也被 transport 实现用；拆分时必须先分清“谁是 core 需要的最小接口”。
3. `rpc_core.h` 是很多文件的根头，一次性大改容易引起宏语义漂移；优先替换副作用型 include，再收尾宏名。

## 6. WP 4.3 — 纳入 RPC 叶子文件（`h_rpc_req.c` / `h_rpc_rsp.c` / `h_rpc_evt.c` / `h_rpc_utils.c` / `h_rpc_slave_if.c`）

### 6.1 目标

在旧头链解开后，优先把 RPC 叶子文件纳入 mock 持续编译与契约级测试。这一组文件比 `h_transport_drv.c` / `h_rpc_wrap.c` 更适合作为门槛 4 的第一批增量，因为它们更接近纯序列化、反序列化、事件分发与轻量驱动桥接。

### 6.2 涉及文件

- `host/core/src/h_rpc_req.c`
- `host/core/src/h_rpc_rsp.c`
- `host/core/src/h_rpc_evt.c`
- `host/core/src/h_rpc_utils.c`
- `host/core/src/h_rpc_slave_if.c`
- `scripts/run_linux_mock_tests.sh`
- `tests/` 下新增对应用例，例如：
	- `tests/test_rpc_req.c`
	- `tests/test_rpc_rsp.c`
	- `tests/test_rpc_evt.c`
	- `tests/test_rpc_slave_if.c`

### 6.3 具体改法

#### Step 1：先只把能直接编的文件纳入 `CORE_SRCS`

推荐纳入顺序：

1. `h_rpc_utils.c`
2. `h_rpc_slave_if.c`
3. `h_rpc_req.c`
4. `h_rpc_rsp.c`
5. `h_rpc_evt.c`

这样一旦编译失败，可以更快判断是：

- 头链残留问题
- 缺少 stub/header
- 测试覆盖不足

#### Step 2：新增最小契约测试，而不是只做编译验证

建议至少覆盖以下场景：

`h_rpc_req.c`
- 非法 Wi-Fi mode 参数
- 空 payload / 长度 0 的错误路径
- heartbeat / scan 参数边界

`h_rpc_rsp.c`
- AP record 拷贝
- custom RPC response 的 `data` / `free_func` 填充
- 错误码透传路径

`h_rpc_evt.c`
- callback 注册/更新/注销
- scan done / sta connected / custom event 的解析
- DPP URI 长度越界保护

`h_rpc_slave_if.c`
- open/write/read/close 的参数校验
- 读信号量为空、底层串口无效等错误路径

#### Step 3：`tests/stubs/` 只补真正缺失的外部边界

本阶段允许继续扩展：

- `tests/stubs/sdkconfig.h`
- `tests/stubs/esp_err.h`
- 极少量缺失的外部声明头

但不建议在这里复制整份旧 `transport_drv.h` 或 `rpc_core.h`。

### 6.4 验证

```bash
bash scripts/run_linux_mock_tests.sh

grep -n 'h_rpc_req.c\|h_rpc_rsp.c\|h_rpc_evt.c\|h_rpc_utils.c\|h_rpc_slave_if.c' scripts/run_linux_mock_tests.sh
```

### 6.5 已知陷阱

1. `h_rpc_rsp.c` / `h_rpc_evt.c` 会同时碰到 Wi-Fi 结构体和 protobuf 结构体；不要把“类型可见”误判成“生产路径已验证”，必须有解析测试兜底。
2. `h_rpc_slave_if.c` 的问题常常不是函数体本身，而是它依赖的 `serial_drv`/`serial_ll_if` 声明边界；一旦出现 include 级报错，先回头看头链，不要急着往 `.c` 里打补丁。

## 7. WP 4.4 — 纳入深水区文件（`h_transport_drv.c` / `h_rpc_wrap.c`）

### 7.1 目标

把剩余最复杂的两个生产文件纳入 Linux mock：

- `h_transport_drv.c`
- `h_rpc_wrap.c`

这是门槛 4 里工作量最大的一步，也是让 `TESTABLE_CORE` 从中段跃迁到 12/13 或 13/13 的关键节点。

### 7.2 涉及文件

- `host/core/src/h_transport_drv.c`
- `host/core/src/h_rpc_wrap.c`
- `host/port/linux/src/h_transport_mock.c`
- `tests/stubs/` 中与 power-save / CLI / BT / feature 宏相关的最小桩
- `tests/` 中新增 transport/wrap 相关用例

### 7.3 具体改法

#### Step 1：扩展 Linux transport mock，不再只做“能链接”

当前 `host/port/linux/src/h_transport_mock.c` 主要是 mock port 支撑。门槛 4 需要把它提升到足够驱动 `h_transport_drv.c` / `h_rpc_wrap.c` 的程度，至少要能：

- 模拟 transport up/down
- 捕获 `esp_hosted_tx()` 发送内容
- 注入 CP init / event / response 数据
- 模拟 bus ready / delayed init 的基本状态机

#### Step 2：为 `h_rpc_wrap.c` 提供事件与回调测试钩子

`h_rpc_wrap.c` 的核心价值不在“能编”，而在它是否正确：

- 把 RPC event 转成 host 事件
- 把 `H_EVENT_HOSTED` / Wi-Fi event 正确投递出去
- 正确处理 DPP / supplicant / custom RPC / mem monitor 分支

因此建议在测试里增加：

- CP init event -> `H_EVENT_HOSTED`
- Wi-Fi event -> `h_event_wifi_post()`
- `rpc_rsp_callback()` 处理失败响应
- custom RPC / DPP 分支在 feature 关闭时不误触发

#### Step 3：把 feature 宏默认关到最小集合

为了先完成门槛 4 主目标，mock 环境应优先收敛到最小 feature 集合：

- DPP
- BT
- host power save
- 其他依赖真实硬件/外部组件的分支

可通过 `tests/stubs/sdkconfig.h` 或脚本编译宏先显式关闭，等主路径 13/13 跑通后再按需补充 feature 分支测试。

### 7.4 验证

```bash
bash scripts/run_linux_mock_tests.sh

grep -n 'h_transport_drv.c\|h_rpc_wrap.c' scripts/run_linux_mock_tests.sh
```

### 7.5 已知陷阱

1. `h_transport_drv.c` 能编译，不等于 transport 状态机可信；至少要有一条从 init 到 transport up 的测试路径。
2. `h_rpc_wrap.c` 最容易出现“事件发出去了，但 event base 错了”的问题；门槛 3 已把 `H_EVENT_HOSTED` / `wifi_post` 契约补齐，门槛 4 必须测它，而不是默认它没问题。
3. 不要让 mock 去假装完整 BT / DPP 功能；门槛 4 首先要拿下主路径，不是把所有 feature 一次补齐。

## 8. WP 4.5 — 取消 `h_rpc_core.c` 的 `H_BUILD_TESTS` 测试专用分支

### 8.1 目标

这是门槛 4 的硬收口项。完成标志不是“还能用 `-DH_BUILD_TESTS` 继续过”，而是：

- `host/core/src/h_rpc_core.c` 不再因为 `H_BUILD_TESTS` 切换到另一套实现
- `tests/test_rpc_core.c` 直接跑生产路径
- `scripts/run_linux_mock_tests.sh` 不再依赖 `-DH_BUILD_TESTS` 才能测 RPC core

### 8.2 涉及文件

- `host/core/src/h_rpc_core.c`
- `tests/test_rpc_core.c`
- `scripts/run_linux_mock_tests.sh`
- `.github/workflows/host-core-test.yml`
- 如需要：Linux mock 中补足 queue/sem/timer/thread/serial 注入辅助

### 8.3 具体改法

#### Step 1：删除顶部双分支结构

当前文件形态是：

```c
#ifdef H_BUILD_TESTS
		... 测试专用简化实现 ...
#else
		... 真实生产实现 ...
#endif
```

门槛 4 的目标是删除这条结构分叉，只保留生产实现。测试如果需要注入点，应通过 mock port / fake serial / helper API 注入，而不是通过另一套实现分支注入。

#### Step 2：把现有测试改成“真生产路径测试”

`tests/test_rpc_core.c` 当前只覆盖了两个轻量场景，而且命中的是测试专用分支。门槛 4 之后至少应扩展到：

- sync request timeout
- async timeout callback 释放路径
- request UID 匹配
- sync response semaphore 唤醒
- init / deinit 的资源清理
- queue/timer/thread 的基本竞态在 TSAN 下不报错

#### Step 3：脚本与 CI 删除 `-DH_BUILD_TESTS`

在最后一个消费者移除后，以下位置都应同步清理：

- `scripts/run_linux_mock_tests.sh`
- `.github/workflows/host-core-test.yml`
- 任何只为了 `H_BUILD_TESTS` 存在的注释、脚本输出、集合口径说明

### 8.4 验证

```bash
grep -n 'H_BUILD_TESTS' host/core/src/h_rpc_core.c scripts/run_linux_mock_tests.sh .github/workflows/host-core-test.yml || echo Clean

bash scripts/run_linux_mock_tests.sh
```

### 8.5 已知陷阱

1. 去掉 `H_BUILD_TESTS` 之后，最先暴露的通常不是业务错误，而是资源生命周期问题：queue 没清、timer 没停、线程未退出。
2. `tests/test_rpc_core.c` 必须从“只测 send/recv”升级到“测 init/send/wait/cleanup 全链路”，否则取消分支后仍然没有真正提高覆盖价值。
3. 删除 `-DH_BUILD_TESTS` 的时机必须放在最后；在头链没解开之前提前删除，只会让整个 mock 编译集同时失效。

## 9. WP 4.6 — Sanitizer 与 CI 收尾

### 9.1 目标

把门槛 4 的收尾动作落到现有 Tier 2 流水线上，而不是再维护一套新的 Linux mock 脚本或 CI job。

### 9.2 当前基线

`scripts/run_linux_mock_tests.sh` 已有：

- ASAN + UBSAN 组合构建/运行
- TSAN 构建/运行

`.github/workflows/host-core-test.yml` 已有：

- `linux-mock-test` 任务
- 直接执行 `bash scripts/run_linux_mock_tests.sh`

### 9.3 具体改法

#### Step 1：继续复用现有 Tier 2

门槛 4 完成时，不需要新建 workflow。只需要确保：

- Tier 2 的脚本输入已经扩展到 13/13
- 脚本输出口径更新为 13/13
- workflow 注释不再写 “current subset”

#### Step 2：必要时把 TSAN 拆为单独 job

若 13/13 后 TSAN 时长明显增加，可以在 workflow 中拆成：

- `linux-mock-test-asan-ubsan`
- `linux-mock-test-tsan`

但这属于性能优化，不是门槛 4 的前置条件。门槛 4 的底线是：**三种 sanitizer 全部通过。**

#### Step 3：文档口径同步

门槛 4 完成时，至少同步以下文档/脚本描述：

- `docs/felix/9.Host通用化实施总路线图.md`

### 9.4 验证

### 9.5 已知陷阱

1. GitHub workflow 现在已经是有效锚点；不要在门槛 4 里再引入一套 GitLab 专用 mock job，否则维护面会翻倍。
2. 若门槛 4 完成后 workflow 注释仍写“current subset”，会造成后续读文档的人误判当前覆盖率。

## 12. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 继续依赖 test-only stub 头覆盖旧结构 | mock 通过但真实结构更乱 | 优先修真实头链，stub 只补边界 |
| `h_rpc_core.c` 去掉 `H_BUILD_TESTS` 后暴露线程/定时器问题 | TSAN/资源泄漏/死锁失败 | 将 4.5 置于最后，并先补足 mock port 能力 |
| `h_transport_drv.c` 被“能编译”误当成“已验证” | 假通过 | 至少补一条 transport state / init event 测试路径 |
| feature 宏分支太多 | 首次纳入时噪音过大 | 先在 mock 下关最小 feature 集合，再按需加回 |
| CI 时长增大 | PR 反馈变慢 | 如有必要把 TSAN 拆成单独 job，但不另起新脚本 |
