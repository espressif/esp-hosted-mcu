# 门槛 4 — Linux mock 覆盖扩展（实施计划 · 轻量骨架版）

> **本文档性质声明**
>
> 这是一个**轻量骨架版**实施计划：仅给出目标、范围、依赖、入口/出口条件、已知风险与待扩写说明。
>
> **不**包含 step 级命令、文件替换块、TDD 步骤等可执行细节。
>
> 真正的 step 级实施计划将在**门槛 3（12 号文档）执行完成后**对本文档进行扩写。

> 本文档的权威来源是 `docs/felix/9.Host通用化实施总路线图.md` 中"门槛 4"小节，本文档不复述其论证过程，只承载对该路线图条目的承接。

## 目标

把 `scripts/run_linux_mock_tests.sh` 中的 `CORE_SRCS` 扩展到与 `host/core/src/*.c` 完全对齐，并取消 `h_rpc_core.c` 的 `H_BUILD_TESTS` 测试专用分支，使 Linux mock 真正覆盖生产主路径，三个口径（portable / testable / 已验证生产路径）在文件集合层面达成一致。

## 范围

### 在范围内（按 9 号路线图 WP 4.1–4.6）

- WP 4.1 — 把 `h_init.c` / `h_api.c` / `h_event.c` / `h_serial_if.c` 等门槛 1–3 已 portable 化的文件全部纳入 mock 编译
- WP 4.2 — 把 `h_rpc_req.c` / `h_rpc_rsp.c` / `h_rpc_evt.c` 纳入 mock 编译
- WP 4.3 — 把 `h_transport_util.c` 纳入 mock 编译
- WP 4.4 — 把 `h_transport_drv.c` 在 mock 下编译（如需，则提供 mock 化的 bus / gpio / irq 替身）
- WP 4.5 — **取消 `h_rpc_core.c` 的 `H_BUILD_TESTS` 测试专用分支**，让 mock 直接走生产路径
- WP 4.6 — 在三个口径文件集合上做交叉校验：`check_core_isolation.sh` 的 `PHASE1_SCOPE`、`run_linux_mock_tests.sh` 的 `CORE_SRCS`、以及"已验证生产路径"声明三者完全重合

### 不在范围内

- 不引入第二非 ESP 真实硬件平台 —— 那是门槛 5 的范围
- 不重构 mock 端 OSAL / event / transport 替身的实现思路 —— 仅在必要时为新增文件补充替身
- 本骨架版**不**展开 step 级命令、文件级替换块、TDD 步骤；这些将在扩写阶段补齐

## 依赖

- **强依赖**：门槛 3 必须先完成。原因：mock 编译能把这些文件纳入的前提，是它们已经在源码层 portable 化；否则纳入即触发 `port_esp_hosted_host_*` 缺失或 ESP 头文件缺失
- **建议先行**：门槛 1 的口径文档（`run_linux_mock_tests.sh` 中头部声明已为本门槛预留位置）
- **可并行**：门槛 3 末期已 portable 化的单文件可以提前纳入 mock，先得反馈，但 WP 4.5（取消 `H_BUILD_TESTS`）必须在 `h_rpc_core.c` 完成 portable 化（门槛 3 WP 3.3）之后

## 入口条件

- 门槛 3 已完成（或至少其中对应 WP 已合入），即将纳入 mock 的目标文件已通过 `check_core_isolation.sh`
- mock 端现有的 OSAL / event / transport 替身仍可用，且与新纳入文件的接口需求兼容
- 当前 `run_linux_mock_tests.sh` 的 `CORE_SRCS` 头部注释已与门槛 1 的口径声明一致（这是 10 号文档已经埋下的钩子）

## 出口条件 / 验收

参照 9 号路线图门槛 4 的验收口径：

- [ ] `run_linux_mock_tests.sh` 的 `CORE_SRCS` 与 `host/core/src/*.c` 完全一致（差集为空）
- [ ] `h_rpc_core.c` 不再含 `H_BUILD_TESTS` 测试专用分支；mock 编译直接走生产实现路径
- [ ] mock 端 ASAN + UBSAN + TSAN 三套构建均通过
- [ ] mock 端既有 unit test 仍通过；为新纳入文件至少补齐基本契约级测试
- [ ] portable 集合（isolation 脚本声明）、testable 集合（mock 编译）、"已验证生产路径"声明三者完全重合，并在文档中显式注明
- [ ] CI Tier 2 能在 PR 上自动跑 mock 测试，作为门槛 4 完成的"持续防回归"

## 已知风险

1. **`h_transport_drv.c` 在 mock 下的替身工作量**：bus / gpio / irq 替身要写得不"假"，否则 mock 通过不等于生产可信；可能比预期工作量大
2. **`H_BUILD_TESTS` 取消后的隐性回归**：当前测试专用分支可能掩盖了某些生产路径下的死锁、竞态、初始化顺序问题，取消之后才会暴露；TSAN 是关键防线
3. **mock 替身与真实硬件行为差异**：mock 通过 ≠ 真实硬件通过；本门槛通过不能替代门槛 5 的真实平台 PoC，需在文档中明确这一点
4. **CI 时长膨胀**：纳入更多文件后 mock 构建/运行时间会显著增加，可能压到 PR 反馈速度；需要监控并在必要时分层（PR 跑 ASAN+UBSAN，定时跑 TSAN）
