# Host 通用框架跨平台移植方案

> **本文档性质**
>
> 本文档是一份面向**任意新平台**的 Host 通用框架移植方案文档，用来回答以下问题：
>
> - 如果要把 Host 通用框架移植到一个新的 MCU / SoC / RTOS / BSP，应按什么顺序推进
> - 平台适配者真正需要实现哪些文件、哪些 contract、哪些验证项
> - 哪些共享层应该复用，哪些内容必须由新平台自行提供
> - 什么时候可以说“这个新平台已经完成 Host 通用框架接入”
>
> 本文档不是 Gate 5 专属 PoC 计划，也不是单一平台的 bring-up 记录。它是一份**通用移植操作方案**，适用于 Zephyr、通用 FreeRTOS、裸机、其他 RTOS，乃至未来的第三、第四个平台。

---

## 1. 目标与适用范围

### 1.1 目标

把当前 Host 通用框架的移植过程，从“读代码后自行摸索”提升为“对任意新平台都有统一入口、统一步骤、统一验证标准”的操作方案。

移植完成后，新平台应满足：

1. `host/core/` 不需要为该平台新增专属逻辑
2. 平台差异收敛在 `host/port/<platform>/` 与平台 app 工程内
3. 新平台至少能跑通 Host 的最小控制面和最小数据面
4. 移植结果可以被其他开发者重复执行，而不是只在当前机器上有效

### 1.2 适用对象

本文档适用于以下场景：

- 为新的 RTOS / BSP 移植 Host 通用框架
- 为新的 MCU / SoC 做 Host 侧 bring-up
- 为第二平台或后续平台建立正式 port
- 评估一个候选平台是否适合作为 Host port 目标

### 1.3 不适用对象

本文档不覆盖：

- slave / co-processor 侧通用化
- Bluetooth / OTA / power save / network split 等扩展特性的功能等价移植
- 单纯的 Linux mock 测试扩展
- 只做概念验证、但不打算进入仓库长期维护的临时 hack

---

## 2. 当前框架基线（2026-05-06）

截至当前主分支，Host 通用框架已经具备以下基础：

- `host/core/` 已经形成可移植核心层
- `host/port/include/h_port_contract.h` 定义了三张 contract vtable
- `host/core/src/h_init.c` 通过 `h_validate_contracts()` 对 port 做 fail-fast 校验
- `host/port/include/h_port_config.h` 作为编译期平台分发入口
- `host/port/esp-idf/` 是现有生产 port 参考实现
- `host/port/linux/` 是现有 mock / 非硬件验证 port 参考实现

当前软件侧已经为新平台移植做好准备，但**不能**因为 Gate 1–4 完成，就直接宣称“任何新平台都已被证明可用”。

原因是：

- Gate 1–4 证明了 core 的可移植性、可测试性和已验证生产路径闭环
- 真正验证“port contract 是否足够支撑新平台真实 bring-up”的，是新平台自身的移植与真实运行结果

也就是说，这份方案文档是“如何把一个平台真正接进来”，而不是“为什么现在已经不需要再接平台了”。

如果需要查看当前仓库里第二平台 PoC 的具体实施步骤与硬件方案示例，可进一步参见 [14.门槛5-第二平台PoC-实施计划.md](14.门槛5-第二平台PoC-实施计划.md) 和 [zephyr/HARDWARE.md](../../zephyr/HARDWARE.md)。

## 3. 移植者最终需要交付什么

对任意新平台，一个完整的 Host port 至少应交付以下几类产物。

### 3.1 Port 代码

最低交付集通常包括：

- `host/port/<platform>/h_port_config.h`
- `host/port/<platform>/h_osal.c`
- `host/port/<platform>/h_event.c`
- `host/port/<platform>/h_transport_<transport>.c`
- `host/port/<platform>/port_init.c`

若平台 API 边界需要额外适配，还可能包括：

- `host/port/<platform>/h_wifi_type_adapt.h`
- `host/port/<platform>/h_wifi_type_adapt.c`

### 3.2 平台 app / build scaffold

除 port 代码外，还需要一个平台自身的集成工程，用来承载：

- 编译系统接线
- 板级配置
- `main()` / bring-up 入口
- 串口日志
- transport 所需的 board overlay / pinmux / Kconfig / defconfig

### 3.2.1 推荐目录骨架（示例）

为了避免移植时把“共享层”、“平台适配层”、“板级集成工程”混在一起，建议从一开始就按下面的结构搭骨架。

下面给出一个“新平台首发走 SPI”的推荐示例。目录名不要求一字不差，但职责边界建议保持一致。

```text
host/
	core/                              # 共享核心层：继续复用，不复制新副本
	drivers/                           # 共享驱动/RPC glue：继续复用
	port/
		include/                         # 共享 contract / wrapper 头文件
		<platform>/
			h_port_config.h                # 新平台编译期配置入口
			h_osal.c                       # OSAL contract 实现
			h_event.c                      # Event contract 实现
			h_transport_spi.c              # 首发 transport 实现（若起手走 SPI）
			port_init.c                    # h_port_* init/deinit 入口
			h_wifi_type_adapt.h            # 按需提供
			h_wifi_type_adapt.c            # 按需提供

common/                              # protobuf / transport header / 共享工具：继续复用

<platform>/
	host_poc/
		README.md                        # 平台 port 使用说明
		HARDWARE.md                      # 板卡、引脚、连线、日志通路
		src/
			main.c                         # bring-up 入口
			app_wifi.c                     # 可选：最小控制面/数据面调用示例
		boards/
			<board>.overlay                # Zephyr 类平台常见落点；其他平台用等价板级配置
		config/
			defconfig                      # 或 prj.conf / sdkconfig.defaults / Kconfig fragment
		CMakeLists.txt                   # 或 Makefile / west build 接线 / 其他构建入口
```

这个骨架有三个关键点：

- `host/core/`、`host/drivers/`、`common/` 继续作为**单一来源**复用，不要为新平台再复制一份
- `host/port/<platform>/` 只负责“把新平台能力接到 contract 上”，不要把业务 app、板级脚本、构建系统杂糅进去
- `<platform>/host_poc/` 只负责板级集成、构建、日志、main 入口和最小验证，不要反过来把共享核心代码拷进去维护

如果目标平台不是 Zephyr，也保持同样原则：

- `boards/<board>.overlay` 可以替换成该平台自己的 BSP 配置文件
- `defconfig` 可以替换成该平台自己的默认配置文件
- 构建入口可以是该平台习惯的 `Makefile`、`CMakeLists.txt`、IDE 工程文件或其他等价形式

### 3.2.2 第一次落地时先创建哪些文件

第一次开始移植时，不建议一上来就铺满全部目录。建议先创建下面这 6 个最小文件，再逐步补齐：

1. `host/port/<platform>/h_port_config.h`
2. `host/port/<platform>/port_init.c`
3. `host/port/<platform>/h_osal.c`
4. `host/port/<platform>/h_event.c`
5. `host/port/<platform>/h_transport_<transport>.c`
6. `<platform>/host_poc/src/main.c`

原因很简单：

- `h_port_config.h` 决定构建是否真的落到新平台，而不是误掉进 Linux fallback
- `port_init.c` 决定 `h_hosted_init()` 的四段初始化顺序是否能被新平台接住
- `h_osal.c` / `h_event.c` / `h_transport_<transport>.c` 是三张 contract 的最小闭包
- `main.c` 让你可以尽早跑起一个最小 bring-up app，而不是只有若干静态库源码

也就是说，**第一次移植的起点不是“复制整个 host 目录”**，而是“先把新平台的最小 port 骨架和一个最小 app 入口立起来”。

### 3.3 文档与记录

每个正式 port 都应至少留下：

- 一份硬件方案记录（如 `HARDWARE.md`）
- 一份平台 port README
- 一份构建与刷写说明
- 一份最小验证记录
- 若是第一个真实非 ESP 平台，还应有 port contract 充分性评估报告

## 4. 新平台移植的总原则

### 4.1 核心层不回退

移植新平台时，默认前提是：

> 不为新平台把平台头文件、平台类型、平台日志宏重新塞回 `host/core/`。

如果一个平台接入需要修改 `host/core/` 才能跑起来，应先判断这是不是：

- 合理的共享 contract 完善
- 还是把平台耦合重新注入 core

只有前者才是允许的。

### 4.2 dispatcher 只做选择，不做实现

`host/port/include/h_port_config.h` 的职责是：

- 判断当前构建环境属于哪个 port
- include 对应的 port config

它不应承载：

- 平台实现代码
- 平台头文件拼装逻辑
- 一大堆只对某个平台成立的函数体

### 4.3 共享层优先复用

对于新平台，以下共享层原则上应优先复用：

- `host/core/src/` 中的 core 逻辑
- `host/drivers/rpc/slaveif/` 中的共享 RPC glue
- `common/proto/esp_hosted_rpc.pb-c.c/h`
- `common/protobuf-c/protobuf-c/protobuf-c.c`

只有当真实移植证明共享层仍残留旧平台假设时，才把问题上升为：

- contract 不充分
- 共享层需要进一步收口
- 或 port 边界仍需再拆分

### 4.4 先走最小主路径，不追求一步到位

任意新平台的第一目标都不是“把所有 feature 都搬完”，而是：

1. 让 OSAL contract 成立
2. 让 event contract 成立
3. 让至少一种 transport 成立
4. 跑通最小控制面
5. 跑通最小数据面

也就是说，新平台移植应优先验证**主路径充分性**，而不是一开始就追求完整功能等价。

## 5. 开始移植前必须锁定的输入条件

任何新平台移植，开始前都必须先锁定以下输入。

### 5.1 平台组合

至少明确：

- Host SoC / board
- RTOS / SDK / BSP
- 编译系统
- 调试接口
- 串口日志接口

### 5.2 transport 路径

只允许先选一条主路径：

- SPI
- SDIO
- UART

起步阶段不建议并行推进多条 transport。

### 5.3 co-processor 侧组合

必须明确：

- slave 芯片型号
- slave 固件配置
- transport 匹配关系
- 连接方式

### 5.4 物理 bring-up 条件

如果是**真实硬件平台**，开始前必须确认：

- 板卡到位
- 连线方案可执行
- 双串口日志可用
- 必要时逻辑分析仪可接入

如果这些条件尚不具备，就不能把状态叫做“正在执行移植”，而应明确写成：

> 计划就绪，待平台条件具备后执行。

## 6. 平台适配的核心对象：三张 contract

新平台真正要实现的不是“若干零散 helper”，而是三张 contract。

### 6.1 OSAL contract

定义位置：`host/port/include/h_port_contract.h`

OSAL contract 负责提供：

- 内存分配
- 对齐分配
- 线程
- 互斥锁
- 队列
- 信号量
- ISR-safe semaphore give
- critical section
- timer
- delay
- 时间获取
- 日志

实现时最常见的问题，不是“API 名字不一样”，而是**语义不一样**。重点关注：

- `thread_delete` 是否真有可用语义
- `timer_start/stop/delete` 是否与 core 假设一致
- `sem_give_from_isr` 是否真能在 ISR 上下文安全调用
- `malloc_align/free_align` 是否满足 DMA 或 cache 要求

### 6.2 Event contract

Event contract 至少要满足：

- handler 注册
- handler 注销
- 普通事件投递
- Wi-Fi 事件投递

新平台不必复制 `esp_event`，但必须满足 core 对事件系统的实际需求：

- 事件可注册
- 事件可异步派发
- handler 上下文可预期

### 6.3 Transport contract

Transport contract 是新平台 bring-up 的核心风险点。

它不仅仅是 bus 传输，还同时涉及：

- bus init / deinit
- SPI / SDIO / UART
- GPIO 配置
- IRQ / 中断注册
- GPIO read / write
- netif create / destroy

这意味着移植者必须把 transport 看成“总线 + 板级 GPIO/IRQ + 网络接入”的组合体，而不是单纯的 SPI 驱动文件。

## 7. 推荐移植流程（适用于任意新平台）

下面是一份推荐的通用流程。无论目标平台是 Zephyr、FreeRTOS、裸机，顺序都建议尽量遵守。

### 阶段 0：锁定目标与条件

输出物：

- 平台组合结论
- transport 选择结论
- 硬件与日志记录

完成标准：

- 不再保留多条主路径
- 所有参与者对目标平台一致

### 阶段 1：建立 scaffold

目标：

- 创建 `host/port/<platform>/`
- 创建平台 app 工程骨架
- 让构建系统能看见这些文件

此阶段不要求跑通硬件，只要求“目录、编译入口、配置入口”成立。

建议在这一阶段直接照着上文 `3.2.1` 的目录骨架落地，不要边写边想目录怎么放。更具体地说：

1. 先创建 `host/port/<platform>/`
2. 再创建 `<platform>/host_poc/`
3. 先把 `h_port_config.h` 接进 dispatcher
4. 再补 `port_init.c` 与三张 contract 的最小空实现
5. 最后才逐步替换成该平台真正的 OS / event / transport 调用

如果需要一个最直接的模板来源，建议只把 `host/port/esp-idf/` 视为**port 层模板**来参考函数形态与文件职责；不要把 `host/core/` 或整个 `host/` 复制成新平台长期分叉。

### 阶段 2：接通 config 分流

目标：

- 让 `host/port/include/h_port_config.h` 能正确落到新平台分支
- 在 `<platform>/h_port_config.h` 中提供平台身份、transport 选择、feature flag、线程栈默认值等常量

完成标准：

- 构建时不再错误地落到 Linux fallback

### 阶段 3：实现 OSAL contract

建议先完成：

- malloc / calloc / realloc / free
- mutex
- queue
- semaphore
- thread
- timer
- log_write

此阶段重点不在功能完整，而在于：

- `h_validate_contracts()` 可以通过
- 基础并发语义不出错

### 阶段 4：实现 event contract

建议采用简单可控的实现：

- 本地 handler 表
- 单独工作线程 / worker queue 派发事件

如果平台没有现成事件框架，这通常比强行模拟原框架更稳。

### 阶段 5：实现最小 transport

起步时只实现主 transport 所需的最小集合。以 SPI 为例，至少要尽快打通：

- `g_h_transport.init`
- `g_h_transport.spi_transfer`
- `gpio_config`
- `gpio_set_intr`
- `gpio_read`
- `gpio_write`

完成标准：

- transport 初始化通过
- 至少一次最小握手不超时

### 阶段 6：处理类型适配边界

如果平台 app 或某些 glue 层仍依赖平台原生 Wi-Fi 类型，就需要明确：

- 是否需要 `h_wifi_type_adapt.h/.c`
- 哪些类型转换是 PoC 主路径必需
- 哪些兼容面暂时不做

建议原则：

- 优先打通 portable `h_*` API 主路径
- 不默认把完整兼容 facade 作为先决条件

### 阶段 7：接入 RPC / protobuf 运行时

这一步的原则是：

- 复用共享 RPC glue
- 复用 generated protobuf 代码
- 复用 protobuf-c runtime
- 不复制第二份 generated code
- 不把测试 stubs 带进生产路径

若平台有 heap / allocator 特殊要求，可先跑默认 allocator 路径，再决定是否封装显式 `ProtobufCAllocator`。

### 阶段 8：平台 app 集成

最小 app 只需要：

- 平台初始化
- `h_hosted_init()`
- 一条最小控制面路径
- 日志输出

不要一开始就在 app 里接全功能业务。

### 阶段 9：验证与收口

最终验证至少应按以下梯度推进：

1. 编译通过
2. `h_validate_contracts()` 通过
3. 最小控制面 RPC 成功
4. `scan → connect → IP` 成功
5. 至少一条最小数据面验证成功

如果这个平台是第一块真实非 ESP 平台，则还需要：

- 输出 port contract 充分性评估报告
- 明确是否需要拆分 transport contract

## 8. 共享层与平台层的推荐边界

### 8.1 默认复用的共享层

新平台默认应复用：

- `host/core/src/`
- `host/drivers/rpc/slaveif/`
- `common/proto/esp_hosted_rpc.pb-c.c/h`
- `common/protobuf-c/protobuf-c/protobuf-c.c`

### 8.2 应放在平台层的内容

新平台应自行提供：

- OSAL 映射
- event 映射
- transport 映射
- 平台 config
- 平台 app / build 接线
- 必要的 type adaptation

### 8.3 明确不允许的做法

以下做法应视为反模式：

1. 为了让新平台跑起来，把平台头文件重新 include 进 `host/core/`
2. 在 dispatcher 里写平台实现逻辑
3. 为新平台复制第二份 protobuf generated code
4. 把 `tests/stubs/` 下的替身带入生产路径
5. 为了图快把多个 transport 同时推进

## 9. 平台验证标准

### 9.1 最低编译标准

至少应满足：

- 新平台 app 可编译
- port 文件可编译
- 共享 RPC glue 可在该构建中通过
- protobuf runtime 已显式接入

### 9.2 最低运行标准

至少应满足：

- `h_hosted_init()` 不崩溃
- 一个最小控制面 RPC 成功
- 真实链路可收到响应

### 9.3 完整接入标准

一个正式的新平台接入，至少应满足：

- `scan → connect → IP / 网络就绪` 成功
- 至少一条最小数据面验证成功
- 构建与运行步骤可复现
- 文档完整

### 9.4 如果这是第一块真实非 ESP 平台

还必须额外完成：

- port contract 充分性评估报告
- transport contract 的 split / no-split 决策

这是因为第一块真实非 ESP 平台不仅是在“接一个 port”，同时也在证明通用框架的 contract 设计是否真的足够。

## 10. 常见风险与应对

### 10.1 OSAL 语义对不上

现象：

- 编译通过，但线程 / timer / queue 行为异常

应对：

- 不只看 API 名称，要对照 core 的实际语义假设

### 10.2 Event 模型与原平台不同

现象：

- handler 注册成功，但事件顺序或上下文不符合预期

应对：

- 先做最小事件框架，不急于复刻原平台事件系统

### 10.3 transport bring-up 难判因

现象：

- 总线看起来有动作，但控制面一直超时

应对：

- 必须保留 Host / Slave 双日志
- 必要时接逻辑分析仪

### 10.4 netif 责任边界不足

现象：

- Wi-Fi connected 事件到了，但拿不到 IP

应对：

- 不要临时 patch 掉，直接记录进 port contract 充分性评估

### 10.5 过早扩 scope

现象：

- 还没跑通主路径，就开始做 BT / OTA / power save

应对：

- 先锁定最小 Wi-Fi 主路径

### 10.6 平台条件并未具备却误判为“正在执行”

现象：

- 文档写成执行中，但板卡、连线、日志路径其实都还没准备好

应对：

- 明确区分“计划就绪”和“条件具备后执行”

---

## 11. 对任意新平台的交付清单

一个规范的新平台移植，建议至少产出以下清单：

- `host/port/<platform>/` 代码目录
- 平台 app 工程骨架
- 一份硬件方案记录
- 一份 port README
- 一份构建 / 刷写 / 日志采集说明
- 一份最小验证记录
- 若为第一真实非 ESP 平台，再补一份 contract 充分性评估报告

---

## 12. 结语

对任意新平台，Host 通用框架移植的关键不在于“把所有代码搬过去”，而在于：

1. 让平台差异稳定地收敛在 port 层
2. 让共享层尽量保持单一来源
3. 让验证结果能证明 contract 足够，而不是只证明编译器足够宽容

如果一个新平台能按本文档的顺序完成接入，并留下完整的验证与文档记录，那么这个平台的移植就不仅是“能跑起来”，而是“进入仓库长期维护也站得住”的正式 port。
